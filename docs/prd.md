## 1. 背景と課題

PoC本体（visit-route-poc）は Firebase・Cloud Functions・Python（OR-Tools）で組んでおり、
デプロイ・費用・認証の準備が重く、協力法人や社内に「触ってもらって意見をもらう」サイクルが遅い。

また、ヒアリング（alca様）で、管理者が割当を決めるときに見ているのは距離だけでなく
**顧客とスタッフの相性・スタッフの特性（資格・経験・得意分野）・顧客の希望（性別・人柄・継続）**だと分かっている。
PoC本体はこのうち「性別希望」と「NG」しか持たず、相性は登録のみ（学習しない）とスコープ外にしている。

本デモ版は次の2つを目的にする。

1. **すぐ触れる**：URLを開くだけで動く。サーバー・ログイン・費用なし。データはブラウザに残す。
2. **割当の条件を柔軟に試す**：ClassClassify のように「項目」と「重み（0〜5）」と「必須」で、
   事業所ごとに違う割当の考え方を管理者自身が組み立て、AI案がどう変わるかをその場で見られる。

デモで集めた反応（どの項目・重みが使われるか）を、PoC本体の要件（相性・希望の扱い）に戻す。

## 2. 対象ユーザー

| 役割 | 説明 | 主な目的 |
|---|---|---|
| デモの利用者（管理者役） | 協力法人の管理者・事務、社内メンバー、営業先 | 架空データで予定と割当を触り、条件を足してAI案と比べる |
| 開発者（松浦） | デモを直してすぐ公開する | main に push → 数分で反映、反応を見て直す |

ログインはない。1台のブラウザ＝1つの事業所。

## 3. 要件

| ID | 要件 | 優先度 |
|---|---|---|
| D1 | 利用者はURLを開くだけで、架空の事業所（仙台・スタッフ8人・訪問先20か所。PoC本体の seed と同じ人物）のデータで使い始められる | Must |
| D2 | 利用者の変更はブラウザ（localStorage）に残り、再読込しても消えない。「デモの初期状態に戻す」でいつでも戻せる | Must |
| D3 | 利用者はデータ一式をファイル（JSON）に書き出し・読み込みできる（別の端末・人へ渡す、バックアップ） | Must |
| D4 | 利用者はスタッフ・訪問先・1日の訪問予定・手作業の割当（担当を選ぶ／列のあいだでドラッグ）を編集できる。順番は開始時刻の順（PoC本体 R3 と同じ） | Must |
| D5 | 利用者は日ごとの稼働時間帯を編集できる（PoC本体 R18 の簡易版：管理者のカレンダーのみ） | Should |
| D6 | 利用者は**項目**を定義できる。項目はスタッフの特性（資格・経験年数・得意分野・性別・言語・ペット可など）と、訪問先の希望・必要条件に使う。種類は「あり/なし」「選択肢から1つ」「選択肢から複数」「数値」（ClassClassify の列の種類にならう） | Must |
| D7 | 利用者は**条件（ルール）**を並べて、それぞれに**重み 0〜5**か**必須**を付けられる。重み0は無効。最低限の条件の型：①訪問先の必要条件（スタッフの項目が条件を満たす）②訪問先の希望（同、満たすと加点）③相性（訪問先×スタッフの ◎/○/△/×）④担当の継続（いつもの担当を優先）⑤負担の均等（スタッフの件数・時間をそろえる）⑥移動時間・待ち時間の重み | Must |
| D8 | 利用者は訪問先×スタッフの**相性**を表（マトリクス）で入れられる。×は「NG」＝必須で外す。PoC本体の性別希望・NG は D6・D7・D8 の初期データとして入る | Must |
| D9 | システムはブラウザ内で**AI案（割当と順番）**を作る。時間の約束・稼働時間帯・必須の条件は破らない。重み付きの条件は、移動時間と同じ物差し（分換算）で足し合わせて最小化する。計算中も画面は固まらず、数秒〜10秒で終わる | Must |
| D10 | 同じ入力と同じ seed からは同じAI案が出る（PoC本体 AGENTS.md の再現性の規約にならう） | Must |
| D11 | 利用者は担当ごとに左に手作業案・右にAI案を並べ、移動時間・待ち・条件ごとの達成/違反の数、合計の点数を比べられる。地図に点線（手作業）と実線（AI）を描く | Must |
| D12 | 利用者は訪問ごとに「なぜこの担当か」（例：相性◎・希望○ 女性・資格✓・継続・移動+12分）を見られ、入らなかった訪問は原因の条件を見られる | Must |
| D13 | 利用者はAI案を「この案を採用」で手作業案に写せる（自動では書き換えない） | Should |
| D14 | 利用者は重みを変えて**すぐに再計算**し、前回の案との差（担当が変わった訪問の数、移動の増減）を見られる | Should |
| D15 | 開発者は main に push すると、テスト→ビルド→GitHub Pages 公開が自動で走る | Must |
| D16 | スタッフのスマホ画面（今日の順番・地図）を、管理者画面から「○○さんの画面で見る」で確認できる（記録はしない） | Could |

## 4. やらないこと（スコープ外）

- ログイン・アカウント・事業所の分離・サーバー保存・複数人での同時編集（1ブラウザ1事業所）
- Firebase・Cloud Functions・Python 最適化サービス・Google Maps Platform（移動時間は直線距離からの概算のみ）
- スタッフの記録（はじめる/おわる）・位置計測・ジオフェンス・勤怠・承認・CSV・実証データ出力・通知
- 実在の個人情報の入力を前提にした機能（注意書きを出す。保存は利用者のブラウザだけ）
- 相性の**学習**（実績から自動で相性を推定する）。相性は人が入れる
- 月次シフトの一括作成（AI案は1日単位。PoC本体と同じ）
- PoC本体へのコードの書き戻し・自動同期（反応と仕様だけ PoC本体の PRD に戻す）
- PWA のオフライン対応・ホーム画面追加（静的サイトとして開ければよい）

## 7. 制約

- 期限：初回デモ用の公開は**着手から1週間以内**（PoC本体 α版＝10月末と並行のため、PoC本体の作業を止めない分量にする）
- 予算：0円（GitHub Pages・GitHub Actions の無料枠）。そのため**公開リポジトリ**が前提（GitHub Free で Pages を使う条件）
- 使う技術：React + Vite + TypeScript、Leaflet（国土地理院の地図。キー不要）、Web Worker。PoC本体の `packages/shared` の純粋関数と seed の生成ロジックを**写して**使う
- 端末：管理者役は PC のブラウザ（Chrome・Edge・Safari の最新）。スマホは表示の確認だけ
- 法規・セキュリティ：架空データのみを同梱する。公開リポジトリに実データ・パスワード・キーを置かない。利用者が入れたデータは端末の外に送らない（外部送信は地図タイルの取得のみ）
