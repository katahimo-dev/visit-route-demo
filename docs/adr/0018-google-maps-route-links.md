# ADR-0018：道順は Google マップの公開のリンク（Maps URLs）を作るだけ（API・キー・サーバーは使わない）

- 日付：2026-10-18
- 状態：採用（利用者が決定（2026-10-18）。細部は推奨どおりに決め、この ADR に記録する）

## 背景
スタッフは訪問先までの道を、住所を地図アプリに打ち直して探している。前に使っていた社内の仕組み
（`gas-root-serach` の `getRouteDetails`・`gas-childcare-visit-app` の `formatRouteLeg`・`buildCurrentLocationMapsUrl`）では、
区間ごとに「道順を見る」「今いる場所から」の Google マップのリンクがあり、便利だった（第9弾の要望）。

このデモは PRD §4 で「Google Maps Platform は使わない（移動時間は直線距離の概算）」、PRD §7・AGENTS.md で
「利用者が入れたデータは端末の外に送らない（外部送信は地図タイルと、押したときの郵便番号・住所の検索だけ。ADR-0016）」としている。
道順の出し方によっては、この2つとぶつかる。

決めること：(1) どう道順を出すか、(2) どこに置くか、(3) 経由地の上限と分け方、(4) 場所の書き方（座標・住所）、(5) メールの長さとの兼ね合い。

## 選択肢
1. 道順の出し方
   - A：**Google マップの公開の「Maps URLs」（`https://www.google.com/maps/dir/?api=1&origin=…&destination=…&waypoints=…|…&travelmode=…`）のリンクを作るだけ。押した人の端末が Google マップ（アプリかブラウザ）を開く**
   - B：Directions API などで経路・時間を取ってアプリの中に出す（キー・費用・サーバーが要る）
   - C：出さない（今のまま）
2. 区間の分数・キロ数
   - A：**Google から取らない（今の直線距離の概算のまま。時間・距離は開いた Google マップで見る）**
   - B：API で取る（1-B が要る）
3. 経由地が多いとき
   - A：**1本の経由地を9件まで（公共交通は0）にし、超えれば前の1本の行き先を次の出発地にして複数本に分ける（「全行程 1/2」）**
   - B：上限を気にせず1本に入れる（落ちる・開かない）

## 決定
1-A、2-A、3-A（利用者が決定）。

- 外部送信の決まりとの関係：アプリはリンク（`<a href>`）を画面・メールの本文に置くだけで、アプリから Google へは何も送らない（通信は起きない）。
  押した人の端末が Google マップを開き、そのとき URL の中の場所が Google に渡る（人が選んで開く。地図アプリに住所を打つのと同じ）。
  だから PRD §7・AGENTS.md の外部送信の決まりは変えない。PRD §4 の「Google Maps Platform は使わない」は、キーの要る API（Directions・Geocoding など）を
  使わないという意味で、公開の URL のリンクはこれとは別物（キー・費用・利用者の登録が要らない）
- URL に入れるもの：場所と移動手段だけ。場所は座標（`lat,lng`。小数6桁まで）があればそれ、無ければ住所の文字。どちらも `encodeURIComponent`（「,」は %2C、経由地の区切りの「|」は %7C）。
  名前・鍵・入り方などの決まりごとは入れない。場所が無ければその区間のリンクは出さない
- 移動手段：〈スタッフ〉の `travelMode`（`TRAVEL_MODES`）を `travelmode` に対応づける（DRIVE→driving・BICYCLE→bicycling・WALK→walking・TRANSIT→transit）
- 経由地の上限（`lib/mapsLink` の `MAPS_MAX_WAYPOINTS`）：9件。根拠は Google の公開の文書（developers.google.com/maps/documentation/urls/get-started、Directions action の
  `waypoints`）の「経由地の数は開く先で変わり、スマホのブラウザは3件まで、それ以外は9件まで」。スマホに Google マップのアプリがあればアプリが開くので 9 にした。
  公共交通は Google マップが経由地付きの経路を出さないので経由地を使わず、全行程を区間ごとの本に分ける。URL も同じ文書の 2,048字（`MAPS_URL_LIMIT`）を超えるときは経由地を減らして分ける。
  作業の環境からは文書に届かず（名前の解決ができない）、上の数は既知の公開の仕様に合わせた（下の見直す条件）
- 置く場所（どれも主ボタンにしない。小さな枠のボタンの見た目のリンク。`target="_blank" rel="noopener noreferrer"`）：
  1. 日の予定のメール（D92・D97）：本文の上に「■Google マップの道順」と全行程（自宅→訪問…→自宅）、各訪問の下に「道順（前の場所から）」、最後に「帰りの道順」。
     長さの目安（ADR-0017 の `mailLimitFor`）を超えるときの段階：全文（全行程＋区間ごと）→ 全文（全行程だけ。「※長いため、区間ごとの道順は省きました。」）→
     要点1＋全行程 → 要点2＋全行程 → 要点2（リンクなし。「…・道順は省きました」）→ 本文なし＋「本文をコピー」。「本文をコピー」は全文（区間ごとも入る）。
     〈スタッフ〉の自宅・移動手段を渡さないときは今までの2段のまま
  2. スタッフ画面（D16・D98）：地図の下に「1日の全行程を開く」（分けたときは「全行程 1/2を開く」…）。各訪問に「自宅から」／「前の場所から」と「ここへ道案内」（出発地を書かない＝今いる場所から）
  3. 日の画面の訪問の詳細（D100）：順番のカード・時間軸の帯を押したときの詳細に、担当の今の案の順番での「前の場所から」（1件目は「自宅から」）と「ここへ道案内」。担当の決まっていない訪問には出さない
- 組み立ては純粋関数：`lib/mapsLink.ts`（`placeParam`・`directionsHref`・`dayStops`・`legLinks`・`tripLinks`・`MAPS_TRAVEL_MODE`・`maxWaypointsFor`）と、メールの本文は `lib/mail.ts` の `dayRouteLinks`・`dayMailText`。
  画面の部品は `components/mapsLinks.tsx`（`MapsLink`・`VisitRouteLinks`）

## 理由とトレードオフ
- 得るもの：
  - 住所を打ち直さずに、訪問先までの道順・1日の回り方を Google マップで開ける（前の仕組みと同じ使い勝手）
  - キー・費用・サーバーが要らず、静的サイトのまま。アプリからは何も送らないので、外部送信の決まりを変えない
  - 時間・距離・渋滞は Google マップが開いたときに出すので、アプリの概算とのずれを人が確かめられる
- 失うもの：
  - アプリの中の分数・キロ数は直線距離の概算のまま（Google の時間とは違う。画面に「時間・距離は Google マップで確かめてください」と書く）
  - スマホのブラウザで開くと経由地は3件までで、4件目以降が落ちうる（アプリなら9件）
  - 公共交通は全行程が区間ごとの本数になる
  - メールに URL が入るぶん本文が長くなり、Windows の目安（2000字）では区間ごとが外れやすい（全行程は残す）
  - 押した人の端末から Google に場所が渡る（人が選んで開く。メールを転送すると自宅の位置も渡る）
- B（API）を採らなかった理由：キーを公開リポジトリ・静的サイトに置けない、費用、利用者のデータを Google に送ることになり PRD §4・§7 を大きく変える
- C（出さない）を採らなかった理由：住所を打ち直す手間が残る（要望の中心）

## 影響
- PRD：D97〜D101 を追加。§4 に Google Maps Platform とは別物である旨と「道順まわり」のやらないこと。§7 に道順のリンクは外部送信に当たらない旨。§8 に見直す条件
- design.md：§2、L3（`lib/mapsLink`・`components/mapsLinks`）、pages（第9弾）、§5「道順のリンク（Maps URLs）」、§7 代替案、§8
- データ：変えない（`DATA_VERSION` は1のまま。場所・移動手段は今の項目を使う）
- 見直す条件：実機（iPhone・Android の Google マップのアプリとブラウザ、PC のブラウザ）で開いて、経由地の上限・公共交通の扱い・住所の文字での検索の合い方を確かめたら、
  `MAPS_MAX_WAYPOINTS`・`maxWaypointsFor`・`MAPS_URL_LIMIT` を見直す。スマホのブラウザで落ちる声が出たら、スタッフ画面だけ上限を3にする。
  アプリの中で Google の時間・距離が要るなら、別の ADR で API とキーの置き場（サーバー）を考える
