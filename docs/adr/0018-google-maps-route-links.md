# ADR-0018：道順は Google マップの公開のリンク（Maps URLs）を作るだけ（API・キー・サーバーは使わない）

- 状態：採用（2026-10-18）
- 関連：PRD D97〜D101、ADR-0016・0017

## 背景
スタッフは訪問先までの道を、住所を地図アプリに打ち直して探している。前に使っていた社内の仕組みでは区間ごとに「道順を見る」「今いる場所から」の Google マップのリンクがあり、便利だった。
PRD §4 は「Google Maps Platform は使わない（移動時間は直線距離の概算）」、§7 は外部送信を地図タイルと押したときの検索だけとしており、道順の出し方によってはこの2つとぶつかる。
決めること：どう道順を出すか、どこに置くか、経由地の上限と分け方、場所の書き方、メールの長さとの兼ね合い。

## 決定
Google マップの公開の「Maps URLs」（`https://www.google.com/maps/dir/?api=1&origin=…&destination=…&waypoints=…&travelmode=…`）のリンクを作るだけにする。押した人の端末が Google マップを開く。区間の分数・キロ数は Google から取らず、直線距離の概算のまま（時間・距離は開いた Google マップで見る）。

- 外部送信の決まりとの関係：アプリはリンクを画面・メールに置くだけで通信しない。押した人の端末が Google マップを開き、そのとき URL の場所が Google に渡る（人が選んで開く。地図アプリに住所を打つのと同じ）。PRD §7 は変えない。PRD §4 の「使わない」はキーの要る API（Directions・Geocoding など）のことで、公開 URL のリンクは別物（キー・費用・登録が要らない）
- URL に入れるもの：場所と移動手段だけ。場所は座標（小数6桁まで）があればそれ、無ければ住所の文字（住所の「|」は経由地の区切りとぶつかるので全角に）。名前・鍵・入り方などは入れない。場所が無い区間はリンクを出さない。移動手段は〈スタッフ〉の `travelMode` を `travelmode` に対応づける（DRIVE→driving・BICYCLE→bicycling・WALK→walking・TRANSIT→transit）
- 経由地の上限：Google の公開文書の「経由地の数はスマホのブラウザで3件まで、それ以外は9件まで」に合わせ、1本の経由地を3件までにする（`MAPS_MOBILE_WAYPOINTS`。超えれば前の1本の行き先を次の出発地にして複数本に分ける。訪問6件なら2本）。4件目以降がスマホで黙って抜けるのを避けるため。9件（`MAPS_MAX_WAYPOINTS`）は PC・アプリと分かる場面用で今は使わない。URL は 2,048字（`MAPS_URL_LIMIT`）を超えるとき経由地を減らして分ける。この環境から文書に届かなかったので、数は既知の公開の仕様に合わせた
- 公共交通は経由地付きの経路を Google マップが出さないので、全行程は出さず区間ごとのリンクだけにする
- 場所の無い地点：全行程では飛ばし、全行程の近くに「場所が未登録の〈利用者さん〉（〇〇さん）は全行程に入っていません」、自宅が無ければ「自宅の場所が未登録のため、全行程は自宅を通りません」と書く
- 自転車：Google マップは日本で自転車の経路を出さないことがあるので、リンクは bicycling のまま近くに「自転車の経路が出ないときは、Google マップで徒歩に切り替えてください。」と添える
- リンクの読み上げの名前は見えている文字で始める
- 置く場所（主ボタンにしない。小さな枠のリンク、`target="_blank" rel="noopener noreferrer"`）：
  1. 日の予定のメール（ADR-0017）：本文の上に全行程（自宅→訪問…→自宅）、各訪問の下に「道順（前の場所から）」、最後に帰りの道順。長さの目安を超える段階は、全文（全行程＋区間ごと）→ 全行程だけ → 要点1＋全行程 → 要点2＋全行程 → 要点2（リンクなし）→ 本文なし＋「本文をコピー」。公共交通は全行程が無いので区間ごと → 要点1 → 要点2 → 本文なし
  2. スタッフ画面：地図の下に「1日の全行程を開く」（分けたときは「全行程 1/2」…）。各訪問に「自宅から」／「前の場所から」と「ここへ道案内」（出発地なし＝今いる場所から）
  3. 日の画面の訪問の詳細：担当の今の案の順番での「前の場所から」と「ここへ道案内」。担当の無い訪問には出さない。今の案が確定した割当と違うときは「今の案（未確定）の順番」と添える
- 組み立ては純粋関数 `lib/mapsLink.ts` と `lib/mail.ts`、部品は `components/mapsLinks.tsx`。データは変えない。細部は design.md

## 検討した案
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| 1-A：Maps URLs のリンクを作るだけ | 住所を打ち直さず開ける。キー・費用・サーバー不要。時間・距離・渋滞は Google が出し、概算とのずれを人が確かめられる | 経由地の上限・公共交通・自転車の制約。アプリ内の分数は概算のまま | 採用 |
| 1-B：Directions API で経路・時間を取って中に出す | アプリ内で完結 | キーを公開リポジトリ・静的サイトに置けない・費用・利用者のデータを Google へ送り PRD §4・§7 を大きく変える | 不採用 |
| 1-C：出さない | 変更なし | 住所を打ち直す手間が残る（要望の中心） | 不採用 |
| 2-A：分数・キロ数は取らない | 外部に頼らない | Google の時間と違う（画面に「Google マップで確かめてください」） | 採用 |
| 3-A：経由地3件で複数本に分ける | スマホで抜けない | 訪問の多い日は2〜3本 | 採用 |
| 3-B：上限を気にせず1本 | 本数が少ない | 4件目以降が抜ける・開かない | 不採用 |

## 結果・トレードオフ・見直す条件
- 得るもの：住所を打ち直さずに訪問先までの道順・1日の回り方を Google マップで開ける。キー・費用・サーバーが要らず静的サイトのまま。外部送信の決まりを変えない
- 失うもの：
  - アプリ内の分数・キロ数は概算のまま。経由地3件で訪問の多い日は全行程が2〜3本。公共交通は区間ごと。自転車は徒歩に切り替える手間
  - メールに URL が入るぶん長くなり、Windows の目安（2000字）では区間ごとが外れやすい（全行程は残す）
  - 押した人の端末から Google に場所が渡る（メールを転送すると自宅の位置も渡る）
- 見直す条件：実機（iPhone・Android の Google マップのアプリとブラウザ、PC のブラウザ）で経由地の上限・公共交通の扱い・住所検索の合い方を確かめ、`MAPS_MOBILE_WAYPOINTS`・`MAPS_URL_LIMIT` と公共交通・自転車の扱いを見直す。全行程の本数が多くて使いにくい声が出たら PC で開く場面だけ上限を9にする。アプリ内で Google の時間・距離が要るなら別の ADR で API とキーの置き場（サーバー）を考える
- 影響：PRD §4 に Google Maps Platform とは別物である旨、§7 に道順のリンクは外部送信に当たらない旨を追記
