# ADR-0016：〈利用者さん〉の郵便番号→住所の補完と、住所→地図のピン（外部の検索サービスを押したときだけ使う）

- 日付：2026-10-17
- 状態：採用（A 案は利用者が決定（2026-10-17）。細部は推奨どおりに決め、この ADR に記録する）

## 背景
〈利用者さん〉の位置（緯度・経度）は、移動時間の概算（直線距離）と地図の線に使う。いまは住所を文字で入れ、位置は地図をクリックしてピンを置くしかない（`PlaceEditor`）。
Excel で〈利用者さん〉をまとめて読み込むと、位置の列が空の人は「未登録」のまま残り、1人ずつ地図で探してクリックするのに時間がかかる。郵便番号から住所を書き起こす手間もある（第7弾の要望）。

PRD §7 は「利用者が入れたデータは端末の外に送らない（外部送信は地図タイルの取得のみ）」としていた（ADR-0001）。住所から位置を出すには、(A) 外部の検索サービスに住所を送るか、(B) 住所と位置の対応表をアプリに同梱するしかない。

決めること：(1) A と B のどちらにするか、(2) 何を・いつ・どこへ送るか、(3) 郵便番号の検索の呼び方（CORS・JSONP）、(4) 失敗したときの扱い、(5) まとめて置くときの呼び方、(6) 郵便番号の持ち方。

## 選択肢
1. 方式
   - A：**外部の検索サービスを、利用者がボタンを押したときだけ呼ぶ**（郵便番号→住所は郵便番号検索サービス、住所→位置は国土地理院の住所検索）
   - B：郵便番号・住所と位置の対応表をアプリに同梱する（外へは送らない）
2. 郵便番号の検索の呼び方
   - A：**fetch（JSON）を先に試し、つながらない（fetch が TypeError＝CORS で読めない・通信できない）ときだけ JSONP（`callback=`）で呼び直す**
   - B：JSONP だけ
   - C：fetch だけ
3. まとめて置く
   - A：**1人ずつ順に、呼ぶたびに 400ms あける。進み具合・止める・失敗した人の一覧。置けた人はその場で store に書く**
   - B：並べて一度に呼ぶ

## 決定
1-A、2-A、3-A（方式は利用者が決定。細部は推奨どおり）。

- 送る先：郵便番号検索（zipcloud。`https://zipcloud.ibsnet.co.jp/api/search?zipcode=1234567`）と国土地理院の住所検索（`https://msearch.gsi.go.jp/address-search/AddressSearch?q=住所`）だけ。どちらもキー不要・無料で、ビルドに秘密情報を入れない
- 送るもの：郵便番号（7桁の数字）か住所の文字だけ。名前・メモ・特性などほかの項目は送らない
- 送るとき：〈利用者さん〉の編集の欄の「住所を探す」「地図に置く」と、一覧の「まとめて地図に置く」を押したときだけ。ボタンの近くに「押すと、郵便番号・住所を外部のサービス（郵便番号検索・国土地理院）へ送ります」と常に出す（毎回の確認ダイアログは出さない。押すこと自体が同意）。開いただけ・入力しただけ・Excel を読み込んだだけでは送らない
- 呼ぶ所：`lib/geocode.ts`（`lookupPostalCode`・`searchAddress`・`jsonp`）と `lib/placeAll.ts`（まとめて置く順番と間隔）。画面（pages・components）から呼ぶ。solver・matching・evaluate・seed・patterns・vacancy・reassign・excel・store からは呼ばない
- JSONP：`<script>` を足して呼ぶので、コールバック名を呼ぶたびに一意（`__vrdJsonp_連番_時刻`）にし、終わったら（成功・失敗・時間切れ・止める）script 要素を消し、グローバルの関数を消す。時間切れの後に遅れて届いた応答は、何もしない関数で受けて捨てる（エラーを出さない）
- 時間切れ：1回の押下ごとに8秒。郵便番号は fetch と JSONP を合わせた全体の締め切りで、JSONP は残りの時間で呼ぶ（最大でも8秒）。時間切れのときは JSONP へ切り替えない（遅いサービスを2回待たせない）。JSONP の script を読み終えても応答の関数が呼ばれていなければ、時間切れを待たずに「応答の形が想定と違います」
- 応答の読み方（既知の仕様）：郵便番号は `{ status, message, results: [{ address1, address2, address3, zipcode }] | null }`。住所 = address1＋address2＋address3。`results` が null・空なら「見つかりませんでした」。住所検索は GeoJSON の Feature の配列で、`geometry.coordinates` が [経度, 緯度]、`properties.title` が住所。緯度・経度が数で範囲内のものだけを候補にし、先頭の5件まで。形が違う（配列でない・数でない）ときは落とさず「応答の形が想定と違います」
- 失敗の種類：入力が正しくない（郵便番号が7桁でない・住所が空）、見つからない、時間切れ、つながらない、応答の形が違う、止めた。どれも日本語の短い文で出し、データは変えない（`lookupMessage`）
- 候補：郵便番号で複数の町が出たとき・住所で複数の場所が出たときは、先頭を入れたうえで、ほかの候補を押して選び直せる（5件まで）
- 住所を入れるとき：見つけた住所（都道府県〜町名）で住所の欄を置き換える。いまの住所が見つけた住所で始まるならそのまま（番地を消さない）。違う住所を書いていたときは「元に戻す」を出す
- ピン：見つけた位置にピンを置き、地図に出す。ずれていれば、今までどおり「位置を消す」→地図をクリックで直す。すでに位置がある人は「住所から置き直す」
- まとめて置く：対象は 位置の無い・段階が「終了」でない〈利用者さん〉のうち、住所か郵便番号のある人。住所が空で郵便番号がある人は、先に郵便番号から住所を探し、住所も書く。1人ずつ順に、呼ぶたびに400ms あける。「止める」で次の呼び出しから止める（置けた人は残る）。置けた人は1人ごとに `update(fn)` で書く（書くときに、まだ位置が無く、住所・郵便番号が探したときのままの人だけ。その間に利用者が位置・住所・郵便番号を直した人は上書きしない。編集の欄を開いたまま保存しても、欄で触っていない位置・住所は store の値（まとめて置いたもの）を残す）。郵便番号で住所は見つかったが位置が見つからない人は、住所だけ書いて「住所だけ入れました」と出す。終わったら 置けた人数・置けなかった人（名前・理由・編集のボタン）・住所も郵便番号もない人、置けた人の地図を出す。画面を離れたら止める
- 郵便番号の持ち方：〈利用者さん〉の `place.postalCode`（`clientPlaceSchema`。文字列・既定 ''・空か7桁の数字）。入力はハイフン・全角数字・「〒」・空白を受けて保存のときに7桁へ直す（`normalizePostalCode`）。〈スタッフ〉の自宅・問い合わせの場所（`placeSchema`）には足さない。Excel の〈利用者さん〉シートに「郵便番号」列（「住所」の前。文字列の列。任意。無い古いブックは空。先頭の0が落ちた数値のセルは0で埋めて7桁に。7桁にできない値はシート名・行付きで止める）
- データの版は1のまま（zod の既定値）。CSP などの設定はリポジトリに無いので足さない（置くときは両ドメインを `connect-src`・`script-src` に足す）

## 理由とトレードオフ
- 得るもの：
  - Excel で読み込んだ〈利用者さん〉を、ボタン1つで地図に並べられる。郵便番号から住所の前半が入るので、書き起こしの手間と誤記が減る
  - 送るのは押したときの郵便番号・住所だけで、送る先と中身がボタンの近くに常に書いてある。デモは架空のデータで使う前提（§7）で、実在の人の名前は送らない
  - 応答の形を確かめてから使い、どの失敗でもデータは変えず、知らせて手で直せる（地図のクリック）
- 失うもの：
  - 「外部送信は地図タイルの取得のみ」ではなくなる（PRD §7・design.md §2 を書き換えた）。実在の住所を入れると、その住所が外部のサービスへ送られる（注記で知らせる。架空データの前提は変えない）
  - 外部のサービスの都合（止まる・仕様が変わる・混む）で使えないことがある。そのときは「つながりませんでした」等を出し、地図のクリックで置ける（今までどおり）
  - JSONP は相手のサービスのスクリプトをこのページで動かす（郵便番号検索が CORS で読めないときだけ）。送る先を固定し、使い終わったら消す
  - 住所検索は住所の文字の一致で、番地の無い・表記の揺れた住所は町の代表の位置になることがある（ずれたら地図で直す）
  - まとめて置くのは1人あたり 0.4〜1秒ほどかかる（100人で1〜2分）。止めて続きは、もう一度押すと位置の無い人だけを置く
- B（同梱）を採らなかった理由：全国の郵便番号（約12万件）と住所の位置の対応表は数十MB になり、静的サイトの読み込みが重くなる。データの更新（毎月の郵便番号の変更）を追い続ける手間もかかる。デモは架空のデータで使う前提で、送るのは押したときだけなので、外部のサービスで足りる

## 影響
- PRD：D86〜D90 を追加。§7 の外部送信を「地図タイルの取得と、利用者がボタンを押したときの郵便番号・住所の検索（郵便番号検索サービス・国土地理院）」に
- design.md：§2、L1・L2・L3、store（既定値）、excel（列）、pages（〈利用者さん〉）、`lib/geocode`・`lib/placeAll`、§5「郵便番号と住所の検索」、エラー方針、タイムアウト、代替案
- データ：`DATA_VERSION` は1のまま
- 見直す条件：外部のサービスが止まる・仕様が変わったら、呼ぶ所（`lib/geocode`）だけを差し替える。実データで使う声が出たら、送る前の確認ダイアログか B（同梱）を考え直す

## 追記（2026-10-18）：空き状況の場所と〈スタッフ〉の自宅にも同じ部品で（PRD D118〜D121）
- 背景：空き状況の画面の場所（問い合わせの場所。データに保存しない一時の入力）は、住所の文字と地図のクリックしかなかった。問い合わせの電話で聞いた郵便番号・住所から点を置きたい（利用者の要望）。〈スタッフ〉の自宅も同じ形（`placeSchema`。郵便番号なし）の入力だった
- 決定：
  - 住所の入力（郵便番号・住所・「住所を探す」「地図に置く」・注記・状態・候補・地図のピン）を1つの部品 `AddressField`（`components/placeLookup.tsx`）にし、決まり（押せない理由・住所の当て方・「元に戻す」・知らせ・候補）は純粋関数 `lib/addressLookup.ts` に置いてテストする。〈利用者さん〉の欄（`ClientPlaceEditor`）はこの部品に郵便番号（`place.postalCode`）を持たせたもので、見た目・動き・data-testid は変えない
  - 送るとき（上の「決定」を広げる）：〈利用者さん〉の編集の欄・空き状況の場所・〈スタッフ〉の自宅の「住所を探す」「地図に置く」と、一覧の「まとめて地図に置く」を押したときだけ。送るものと送る先、注記、失敗の扱い、時間切れは今までどおり。空き状況の注記の後ろは「条件などほかの項目は送りません」。呼ぶ所は今までどおり `lib/geocode.ts` の1か所（`lib/addressLookup` は外部を呼ばない）
  - 郵便番号の持ち方：空き状況の場所・〈スタッフ〉の自宅には**足さない**（上の「郵便番号の持ち方」のまま）。空き状況では画面の状態だけに持ち、「仮の〈利用者さん〉として押さえる」で〈利用者さん〉を作るときだけ、7桁にできれば `place.postalCode` に写す。自宅では部品の中だけに持ち、保存しない（見出しに「保存しません」）。契約（`src/contracts/`）・`DemoData`・データの版は変えない
  - 空き状況の計算（`vacancyOf` など）に渡すのは、位置があるときの住所・位置だけ（`Place`）。点が無ければ今までどおり目安。郵便番号を打っただけでは計算し直さない
- 理由：同じ入力を画面ごとに作ると、文言・押せない理由・住所の当て方がずれていく。部品と決まりを1つにすれば、〈利用者さん〉で確かめた動きがそのまま使える。郵便番号を自宅・問い合わせの場所に足すと契約・Excel の列・版の移行まで広がるが、要るのは住所を探す手がかりだけなので、保存しない一時の入力で足りる
- 失うもの：〈スタッフ〉の自宅の郵便番号は開き直すと空に戻る（保存しないため）。保存したいという声が出たら、`placeSchema` を使う自宅を `clientPlaceSchema` と同じ形にする（契約・Excel の列・版を見直す）
