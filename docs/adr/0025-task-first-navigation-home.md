# ADR-0025：UI/UX 改善：やりたいことから入る導線（ホーム「今日やること」はその第1弾）

- 日付：2026-10-18
- 状態：採用（利用者の依頼（2026-10-18）「直感的にやりたいことが操作できるように」。第1弾のホームは PRD D141〜D145。区切り2の進み具合の帯は PRD D151〜D155、区切り3の「案を変える ▾」と比較への道筋は PRD D156〜D160、区切り4の作り直しの帯は PRD D161〜D166、区切り5の「欠勤・キャンセル」の欄は PRD D167〜D172、区切り6の言葉と案内は PRD D173〜D177（下の追記）。区切り7のメニューとコマンドパレットは ADR-0027（PRD D178〜D183）。区切り8a の空き状況の段階化と週の切り替えは PRD D184〜D188、区切り8b のスマホの月の一覧・地図ボタン・ファイル選択・初回の案内ツアーは PRD D189〜D193（下の追記）。区切りはすべて済んだ。そのあと利用者の要望（2026-10-18）で、右の欄の確定のボタンの帯を内容に付いてこさせる（PRD D194〜D197。下の追記））

## 背景
画面の監査（2026-10-18）で、やりたいことに届くまでの迷いが分かった。

- 起動すると案内なしでいきなり日の画面（`#/plan`）になる。今月の準備がどこまで進んでいるか、次に何をすればよいかは、月の画面の「今月の準備」（PRD D59）を開かないと分からない
- メニューは「データの種類」（〈利用者さん〉／〈スタッフ〉／割当の設定）で並ぶ。やりたいこと（月を組む・欠勤に対応する・問い合わせに答える）とは合っていない
- 同じ操作が複数か所にある（案を作る＝月の見出しのボタン・今月の準備の②・日の「案を変える▾」。確定＝日と月の③）。逆に「急な欠勤」は列の見出しの小さいボタンで見つけにくい
- 制約：新しい保存データを増やさない（データの版・Excel・JSON の書き出しを変えない）。データを書き換えるのは store だけ。既存の画面の URL・e2e を壊さない。スマホは表示の確認が主（PRD §7）

## 選択肢
1. 案A：起動したときの画面に「ホーム（今日やること）」を足し、今の状態から次の一手をカードで出す。カードは既存の画面・既存の操作（月のまとめて作るの欄・右の欄、日の画面）へ移るだけ。判定は純粋関数で、月の画面と同じ数え方
2. 案B：日の画面の上に「今日やること」の帯を足す（起動は今のまま日の画面）
3. 案C：メニューを先にやりたいこと順に並べ替える（ホームは作らない）
4. 案D：最初にツアー（案内の吹き出し）を出す

## 決定
案A。決まりは `lib/home.ts`（純粋関数）の1か所：見る月 `homeMonths`（今月。残り7日以下なら来月も）・見る日 `homeDays`・カード `homeTasks`（要対応 → 今日の予定 → 確定していない日 → 案を作る）。日の状態は月の画面の計算を `lib/useDayStatuses.ts` に切り出して共通に使う（要対応・確定の件数が月の画面と食い違わない）。月の画面の操作は `?do=batch|attention|unconfirmed` で開き、1回行ったら URL から消す。起動（`#/`）と知らない URL の行き先をホームに。メニューの先頭とスマホの下のタブ（5つ）に「ホーム」。

## 理由とトレードオフ
- 得るもの：開いた人が1画面で「次に何をするか」が分かり、1クリックでその操作の画面に着く。新しい保存データが無いので、データの版・書き出し・移行は変わらない。月の画面と同じ数え方なので数字が食い違わない。カードの行き先は既存の操作なので、機能を二重に作らない
- 失うもの：起動のたびに今月（月末は来月も）の日を compile・採点する（月の画面と同じ重さ。8人・約17件／日の一月で 500ms 以内）。起動しても日の画面を開かないので、今日の案の自動作成（PRD D52）は今日のカードを押したときになる。スマホの下のタブが5つになり、1つの幅が狭くなる（390px で78px）
- 案B は日の画面がさらに長くなり、月の準備（来月の訪問を作る）が日の画面の話でなくなる。案C は並べ替えだけでは「今の状態」が分からない（第7弾で別にやる）。案D は一度見たら終わりで、毎日の「次の一手」にならない（第8弾の初回ツアーで補う）

## 影響
- 画面：`pages/HomePage`（`home.css`）、`app/App.tsx`（ルート `/home`・`*` の行き先・メニューの先頭）、`lib/nav.ts`（`BOTTOM_TABS` に `/home`）、`styles.css`（下のタブを5列）、`pages/MonthPage`（`?do=` と、日の状態の計算を `lib/useDayStatuses` へ移す。見た目は変えない）。データ・契約（`src/contracts/`）・store は変えない
- 確かめ：`src/lib/home.test.ts`（何も無い・全部済み・一部済み・月末）、`scripts/e2e-home.cjs`、`scripts/e2e-mobile.cjs`（下のタブ5つ）
- 見直す条件：カードが多すぎる（月ごとに3枚×2か月）という声があれば、月ごとのカードを1枚にまとめる。起動の重さが気になる事業所（数十人・日に数十件）では、ホームは今月の今日から2週間だけ見るかを決める

## レビュー（PR #36）で直したこと（追記）
- 確定していない日の数え方：ホームは案のある日（未確定・未確定の変更あり）だけ数えていたため、月の「今月の準備」の③・右の欄（訪問があって確定済みでない日。案の無い日も含む）と日数がずれた（ホームで2日、開いた欄には5日）。ホームを月の画面に合わせ、同じ日数・同じ並びにした。案の無い日は「案をまとめて作る」のカードにも出る（重なってよい）。月の③の意味は変えない
- `?do=batch`：この月に訪問が無いときだけでなく、まだ案の無い日の対象が0日のときも欄を開かない（見出しのボタンの欄を開いても「作り始める」が押せないため）
- ホームは `useDayModel(今日)` をやめ、compile が読むデータだけを取る `useCompileInput` を使う（今日の問題を二重に compile しない）

## 区切り2：予定に共通の進み具合の帯（追記。2026-10-18。PRD D151〜D155）

### 背景
案を作る入口が3か所（月の見出しの「◯月の案をまとめて作る」・月の「今月の準備」の②「まとめて作る」・日の「案を変える▾」）、確定が2か所（日の「この割当で確定」・月の③）にあった。月の画面では同じ数字（案のある日・確定した日）が「今月の準備」と見出しの要約に並び、週・日の画面では今月がどこまで済んだか・次に何をするかが分からなかった。

### 選択肢
1. 案A：月・週・日の見出しの下に同じ形の細い帯（見ている月の今日以降の 訪問・案・確定・要対応＋次の一手のボタン1つ）を置き、月の「今月の準備」（①〜③）と見出しの主ボタンを帯にまとめる。「訪問だけ作る」はまとめて作るの欄の中へ
2. 案B：帯は足すが「今月の準備」は残し、役割を分ける（帯＝要約と次の一手、今月の準備＝①〜③の操作のボタン）
3. 案C：週・日には帯を置かず、［月｜週｜日］の「月」に件数のバッジを付ける

### 決定
案A。決まりは `lib/progressBand.ts`（純粋関数）：次の一手 `bandNext`（作っていない訪問・案の無い日 → まとめて作る、手当てが要る要対応 → 要対応を見る、確定していない日 → 確定していない日を見る、見るだけの要対応 → 要対応を見る、無ければ済み）・`urgentCount`・見る月 `bandMonth`（選んでいる日付の月。週は週の中の選んでいる日の月）・移る先 `bandHref`（月の画面の `?do=`）。見た目は `components/progressBand.tsx` の `ProgressBand`（月の画面は自分で数えた値を渡して主ボタン、欄は画面の中で開く）と `ScheduleBand`（週・日。`useDayStatuses`・`monthProgress`・`attentionList` で数える）。月の画面の `?do=batch` は、まだ案の無い日が無ければ「確定していない日をすべて作り直す」で開く（D143 を直す）。

### 理由とトレードオフ
- 得るもの：どの予定の画面でも同じ場所・同じ数で「今どこまで済んだか」と「次の1つ」が分かる。数え方は月の画面・ホームと同じ部品（`useDayStatuses`・`monthProgress`）なので食い違わない。月の画面の「まとめて作る」は帯の1か所になり、同じ数字が2か所に並ばない。新しい保存データ・契約は無い
- 失うもの：月の画面の「今月の準備」の①〜③の段の並び（手順の見せ方）と、D80 の凡例つきの積み上げが無くなる（帯の下の縁の細い積み上げと、数字の✓で代える）。「訪問だけ作る」は欄を開かないと押せない（使う人は少なく、欄の中に「案は作らない」と書いて置く）。週・日の画面を開くと、その月の今日以降の案のある日を compile・採点する（月の画面と同じ重さ。`useDeferredValue` で画面を描いた後に回し、日ごとの覚えで手直しのたびに月全体を数え直さない。e2e で 3 秒以内・確定の操作は 1.5 秒以内を確かめる。手元では案が全部ある月で 100ms ほど）
- 案B は帯と今月の準備で同じ数字が2か所に並び、「まとめて作る」の入口も2か所のまま（今回の問題が残る）。案C は週・日で次の一手が押せない
- 帯の次の一手は月の画面だけ主ボタンにする。日の画面は「この割当で確定」が主ボタンなので、帯は普通のボタンにして主ボタンを1つ（多くて2つ）に保つ。日の確定は今のまま日の画面で行い、帯は「この日 未確定（「この割当で確定」で確定）」と状態を見せるだけ（確定の入口を増やさない）

### 影響
- 画面：`components/progressBand.tsx`（`progressBand.css`）を足す。`pages/MonthPage`（見出しのボタンと `MonthPrep`・`PrepStep` をやめ帯に。`openBatch` を帯と `?do=batch` で共通に。欄に「訪問だけ作る」）、`pages/WeekPage`・`pages/PlanPage`（見出しの下に `ScheduleBand`）。データ・契約（`src/contracts/`）・store は変えない。`components/glance` の `PrepBar`（今月の準備の積み上げ）は使う画面が無くなったので消す（色の CSS `.prep-bar`・`.prep-part` と `lib/glance` の `prepParts` は帯の積み上げで使う）
- 確かめ：`src/lib/progressBand.test.ts`、`scripts/e2e-progress.cjs`。`scripts/e2e-home.cjs` の「③の日数」は帯の確定していない日数で確かめる
- 見直す条件：帯の次の一手が「要対応を見る」のまま動かない（欠勤のある日は手当てを終えても要対応に残る）という声があれば、見るだけの要対応を次の一手から外す。週・日の帯が重いという事業所（数十人・日に数十件）では、帯を今日から2週間だけ数えるかを決める

### レビュー（PR #38）で直したこと（追記）
- 月の見出しの下の要約（月全体）が帯（今日以降）と同じ言葉「訪問」「案のある日」で違う数を並べていたので、要約は帯に無い「入らない・当日キャンセル」（月全体）だけにした
- 済んだ「案 ✓」から開いたとき、欄の既定が「確定していない日をすべて作り直す」（手直しを捨てうる操作）になっていた。既定はいつも「まだ案の無い日だけ」（0日でも）とし、作り直しは利用者が選んだときだけにした。欄を開かないのは、作っていない訪問・案の無い日・確定していない日がどれも無いときだけ
- 読み上げ：数字のリンクに押すと何が起きるかの aria-label、✓ の「済」、手当てが要る要対応の「要手当て」。aria-live の領域は最初から空で置き、数え直して変わったときだけ中身を入れる（開いたときには読まない）
- Ctrl・⌘・Shift・中ボタンのクリックは横取りせずブラウザに任せる（新しいタブで月の画面）
- 週・日の帯の定期パターンの展開は、読むもの（定期パターン・訪問・〈利用者さん〉）と月で覚え（`lib/month` の `expandMonthVisits`）、案の手直し・確定のたびに月全体を展開し直さない
- `scripts/e2e-home.cjs` は月末7日以内（来月のカードも並ぶ）と、今月の残りが今日だけ（カードが日の画面へ移る）でも通るようにした。`scripts/e2e-progress.cjs` も同じ日付で通す

## 区切り3：「案を変える ▾」を目的の言葉で選ぶ・比較への道筋（追記。2026-10-18。PRD D156〜D160）

### 背景
日の画面の「案を変える ▾」は10の項目（プリセットごとの案・他の条件でも作る・AI案を作り直す・固定を残して組み直す・AI案に戻す・前の同じ曜日からコピー・案を比べる・条件を調整する）を区切りの線だけで並べていた。名前が仕組みの言葉（「固定を残して組み直す」「AI案に戻す」）で、開いて読むまで「AI に作り直させる」のか「手で変える」のか、押すと手直しが消えるのかが分からなかった。比較の画面（`#/compare`）はメニューに無く、入口は「案を変える」の中だけ。案が1つしか無いと「比べるには案が2つ以上いります」と出るだけで、その場では何もできなかった。

### 選択肢
1. 案A：項目は今のまま（機能を足さない）、目的の言葉の名前と1行の説明・見出し付きのまとまりに並べ直す。押せない項目は理由を見える文で。比較の画面は案が1つなら「もう1案作って比べる」（既存の Worker の計算で記録に足すだけ）。サイドのメニューに比較は足さない
2. 案B：「案を変える ▾」をやめ、目的ごとのボタン（作り直す・比べる・戻す）を操作の行に並べる
3. 案C：案A に加えて、サイドのメニューの「予定」に「比較」を足す
4. 案D：比較の画面の「もう1案作って比べる」は日の画面へ移って作らせ（`?do=` のように）、作り終えたら比較へ戻す

### 決定
案A。文の決まりは `lib/planMenu.ts`（純粋関数）：`createText`・`resolveText`・`revertText`・`compareText`・`presetDescription`（名前・1行の説明・押せない理由）と、比較の画面の選択肢 `anotherPlanOptions(presets, base, current)`（今ある案が AI が出したままの記録で、いまのデータでも同じ問題（`problemKey` が記録の inputKey と同じ）なら同じ条件のプリセットを除き、今の条件がどのプリセットとも今ある案とも違えば「今の条件（重み）で作る」）。部品 `components/MenuButton` に、項目の説明（`description`。押せないときは理由に差し替え）と、まとまりの見出し（`group`。`role="group"`＋aria-label）を足した。比較の画面は `runSolve`（日の画面と同じ種・反復回数）で作り、`lib/runs` の `addRun` で記録に足すだけ（今の案・条件は変えない）。「固定を残して組み直す」は「固定した訪問は残して、ほかを作り直す」と名前を事実に合わせ、固定が無くても押せるまま（戻す先を残すので作り直すとは結果が違う）。固定にならない手直しがあるかは `hasUnpinnedEdits`（純粋関数）で決め、あれば説明に書いて確認ダイアログで確かめる。

### 理由とトレードオフ
- 得るもの：開いたときに目的（もう一度作らせる・手直しを残して作り直す・別の考え方に切り替える・比べる・戻す）で選べ、押すと何が変わり手直しが消えるかを押す前に読める。押せない理由が title だけでなく見える文になった。比較は案が1つでもその場で2つめを作れ、行き止まりが無くなった。新しい保存データ・契約・計算は無い（文と並びと、既存の計算の呼び方だけ）
- 失うもの：一覧が説明のぶん縦に長くなる（最大で画面の7割、中を巻く）。プリセットの項目の説明は手直しがあるとき「手直しと固定は消えます」が考え方の数だけ並ぶ（押す前に必ず目に入る方を取った）。「固定した訪問は残して…」は固定にならない手直しがあると確認が1回増える。比較の画面で作った案は今の案にならず、今の案にするには表の「予定の画面で開く」をもう1回押す（比べる前に今の案を変えないほうを取った）
- 案B は日の画面の操作の行が長くなり、主ボタンの「この割当で確定」と並んで目立ちすぎる（主ボタンは1画面1つの決まり）。390px で行が折れる。案C は区切り7でメニュー全体を用途ごとに並べ替える予定で、今足すと並びを2回変える（比較は「日の案」を前提にした画面で、メニューから日付を選ばずに開くと迷う）。案D は画面を行き来し、比較の画面の「その場で」にならない
- 計算の場所：比較の画面の計算は日の画面とは別に持つ（画面を離れたら止め、結果は捨てる）。日の画面と比較の画面は同時には開かないので、同じ日の計算が重なることは無い

### レビュー（PR #39）で直したこと（追記）
- 「手で動かした所は残して、ほかを作り直す」は名前が動きと違った（組み直しは固定しか残さず、「入らなかった訪問」へ移した・固定を外した手直しは確認なしで消えていた）。名前を「固定した訪問は残して、ほかを作り直す」にし、固定にならない手直しがあれば説明に「固定していない手直しは消えます」と書いて確認ダイアログで確かめる（`hasUnpinnedEdits`）
- 固定が無いと押せなくした変更は戻した。組み直しは AI が出したまま（戻す先）を残すので、作り直すとは結果が違う（D156 の「機能を減らさない」を優先）
- 比較の画面で除くプリセットは、今ある記録がいまのデータでも同じ問題のとき（`problemKey` が inputKey と同じ）だけにした。計算中に日付を変えたら計算をやめて捨てる（進み具合と「止める」が見えなくなるため）。止めた案の知らせを分けた。今の案が無い日の「まとめて作る」の説明を「一番点の高い案を今の案にします」に

### 影響
- 画面：`components/MenuButton.tsx`（`description`・`group`、名前は aria-labelledby・説明は aria-describedby、幅は中身に合わせて最大 400px）、`pages/PlanPage`（項目の並びと文を `lib/planMenu` から。案内の文の項目名をそろえた。右の欄の「他の条件でも作る」も「まだ作っていない考え方をまとめて作る」に）、`pages/ComparePage`（`compare-another`：考え方の選び・主ボタン・進み具合と止める・作れない理由。lead の文）。データ・契約（`src/contracts/`）・store は変えない
- 確かめ：`src/lib/planMenu.test.ts`、`scripts/e2e-plan-menu.cjs`
- 見直す条件：一覧が長くて目的の項目を探しにくいという声があれば、プリセットの項目を「別の考え方に切り替える…」の1項目にまとめて右の欄（条件を調整する）のカードへ寄せる。比較の画面で作った案をそのまま今の案にしたいという声が多ければ、作ったあとの知らせに「今の案にする」を足す。区切り7でサイドのメニューに比較を足すかを決め直す

## 区切り4：条件を変えたら、その場で影響と「作り直す」を出す（追記。2026-10-18。PRD D161〜D165）

### 背景
条件の重み（#/rules）・相性・稼働時間・訪問の種類・特性の項目・〈スタッフ〉・〈利用者さん〉を変えても、案はそのまま残る。作り直す入口は月の画面の「条件が変わった日を作り直す（N日）」だけで、変えた画面から案へ戻る導線が無かった。
しかも今の「条件が変わった」（D43。`lib/month` の `planStale`）は、記録の条件（`run.rules`）でいまのデータから作った問題のキーが記録の `inputKey` と違うかで決めるので、訪問・〈スタッフ〉・稼働時間・相性・特性・種類の変更は拾うが、条件の重み・必須・プリセットの重みの変更は拾わない（記録の条件をそのまま当てるため）。重みの画面で変えても「条件が変わった日」は0日のままだった。

### 選択肢
1. 案A：設定の画面の上に帯を出し、数えるのは月の要対応と同じ部品（`useDayStatuses`）。D43 の判定に「作った条件（重み・必須）が変わった」を足す（プリセットで作った案はそのプリセットが、いまの条件で作った案はいまの条件が変わったら）。［作り直す］は月の画面の欄（`?do=stale`）を開くだけ
2. 案B：帯は出すが、判定は今の D43 のまま（重みの変更では出ない）
3. 案C：重みの判定は「いまの条件（`data.rules`）と記録の条件が違う」にする（日の画面の注記「作ったあとに条件が変わりました」と同じ）
4. 案D：帯の［作り直す］でその場で作り直す（月の画面へ移らない）

### 決定
案A。決まりは `lib/rebuildBand.ts`（純粋関数）：出す画面 `REBUILD_PATHS`・`showsRebuildBand`、数える日 `rebuildDays`（今日以降の今の案のある日）、`rebuildSummary(statuses, today)`（`DayStatus.stale` の日を未確定（確定した割当なし）と確定済み（確定済み・未確定の変更あり）に分ける）、`rebuildText`、`rebuildAction`（未確定の最初の日の月の `/month?ym=…&do=stale`、未確定が無ければ `do=attention` の「要対応を見る」）。判定は `lib/month` の `ruleSetKey`・`currentRuleKeys`・`rulesStale`（記録の `presetId` のプリセットがいまもあればそのプリセットをいまの条件に当てたものと比べ、無ければいまの条件と全プリセットのどれにも当てはまらないか。名前は見ない）を `useDayStatuses` で `planStale` に足す（覚えの外で決める）。見た目は `components/rebuildBand.tsx`（App の main の中、設定の画面だけ・key は画面）。

### 理由とトレードオフ
- 得るもの：変えたその画面で、影響する日数と次の一手（作り直す）が分かる。数は月の要対応・進み具合の帯・ホームと同じ部品なので食い違わない。重み・プリセットの変更も「条件が変わった」に入り、月の「条件が変わった日を作り直す」で直せる。新しい保存データ・契約は無い（［後で］も画面の中の状態だけ）
- 失うもの：月の要対応に「条件が変わった」が今より出やすくなる（プリセットの重みを変えると、そのプリセットで作った今日以降の案のある日がすべて出る）。条件の重みの画面の重み（いまの条件）を変えても、プリセットで作った案は出ない（作り直しても点数の基準のプリセットで作るので同じ案になるため。いまの条件で作るのは日の画面の「AI にもう一度作らせる」で、日の画面の注記は今どおり）。いまの条件がたまたまプリセットと同じ重みのときに日の画面で作った案は、記録上そのプリセットの案になる（`presetId`）。設定の画面を開くたび・データを変えて 600ms 止まるたびに、今日以降の案のある日を compile・採点する（月の画面と同じ重さ。日ごとの覚えで、条件と関係ないデータの変更では compile し直さない）
- 案B は重みの画面で帯が出ず、今回の問題（重みを変えても作り直す導線が無い）が残る。案C はプリセットで作った案（月のまとめて作る・日の自動作成）がいまの条件と違う重みなら最初から全部「変わった」になり、作り直してもまたプリセットの重みで作るので消えない。案D は設定の画面から月全体の計算を始め、進み具合・止める・手直しを捨てる確認を設定の画面に二重に持つことになる（月の画面の欄で作り始める形なら、確認と止めるは今のまま）

### 影響

### レビュー（PR #40）で直したこと（追記）
- 判定の決め直し：記録の `presetId` は「作ったときに重みが一致した最初のプリセット」（`lib/runs` の `addRun` が `presetOf` で付ける）で、使ったプリセットそのものではない。これに頼ると、「プリセットとして保存」で標準と同じ重みのプリセットを作って基準にし、案を作ったあとに標準を変えると、基準で作り直しても「変わった」が消えなかった（作り直した案の `presetId` がまた標準になる）。`rulesStale` は記録の条件のキーが「いまの条件」にも「いまの条件に各プリセットを当てたもの」にも無いときだけ true にした（作ったときの条件がもうどこにも無い）。作り直しはいつも基準のプリセットで作るので、作り直した案は必ず当てはまる（`src/lib/month.test.ts` に手順どおりのテスト）。点数の基準を切り替えただけでは変わらない（PRD D161 に書いた）。いまの条件がプリセットと同じ重みのあいだはそのプリセットを変えても「いまの条件」に残るので出ない（D166 の案内は出ない。e2e はいまの条件を動かしてからプリセットを変える）
- 日の画面の作り直すの帯（`planIsStale`）も同じ `rulesStale` を使い、月・ホーム・帯と揃えた。［作り直す］（`remakeStale`）は記録の古い条件でなく基準のプリセットで作る（古い条件で作ると、条件がもう無いので「変わった」が残る）
- 帯（未確定の日があるとき）・月の欄・日の画面の帯に「点数の基準のプリセット「〈名前〉」で作り直します（いまの条件で作った案も「〈名前〉」の案になります）」（`rebuildWith`）
- いまの条件の案内（PRD D166）：条件の重みの画面で、いまの条件がどのプリセットとも違えば、同じ帯の2行目に使われ方と［今日の案をいまの条件で作り直す］（日の画面の `?date=…&do=recreate`。`recreate` を呼び、その日の自動作成はしない）・［プリセットとして保存］（`SavePresetForm`）
- 帯の未確定は確定した割当が無い日（`manualPlans`）で数え、`DayStatus.stale` は計算に入れる訪問がある日だけにした（`batchTargets` の 'stale' と同じ。帯の未確定＝ `?do=stale` の対象）
- 貼り付いたとき：`top: var(--header-h)`（隙間なし）。帯がある間は帯の高さを ResizeObserver で `--rebuild-band-h` に入れ、html の `scroll-padding-top` を上の帯＋帯の高さに（Tab で入った入力欄が帯の下に隠れない。帯が消えたら戻す）
- 数え直しの重さ：`useDayStatuses` の日ごとの覚えをモジュールに置き（日付ごとに最近3件。点数の物差しの条件は中身（JSON）で比べる）、画面を移っても使う。数える日数は減らさない
- 0日になって帯が消えるときは「影響する日は無くなりました」を1度だけ読み上げる

- 判定の直し（同日）：上の決め直しでは「いまの条件」を誰に対しても照らしたため、いちばんよくある流れ（初期状態＝いまの条件が標準と同じ重みのまま、標準のプリセットの重みを変える）で帯が出なかった。照らす鍵は「いまの条件に各プリセットを当てたもの」とし、「いまの条件」そのものは記録の `presetId` が null の案（作ったときにどのプリセットとも一致しなかった＝いまの条件で作った案）だけに照らす。プリセットで作った案（`presetId` は一致した最初のプリセット）は、いまの条件が古い重みのままでもプリセットが変われば「変わった」。作り直した案は基準のプリセットの鍵と一致するので消える（「プリセットとして保存」→基準→標準を変える の流れでも、作った重みが「マイ」に残るので出ず、出たときは作り直すと消える）。いまの条件で作った案は、いまの条件が変わらない限り出ない

### 再レビュー（PR #40）で直したこと（追記）
- 記録の `presetId` の意味を「最後に作ったとき（同じ記録を使い回したときも）に重みが一致した最初のプリセット（無ければ null）」にした（`contracts/data.ts` のコメント）。`lib/runs` の `addRun` は、同じ条件・種・固定・結果の記録を使い回すときも `presetId` を今の時点の `presetOf` に書き直す。自動作成（標準）→ 標準の重みを変える → いまの条件（古い標準の重み）で作り直して同じ案になると、使い回した記録が presetId=標準 のまま残り「条件が変わった」が消えなかったため
- 日の画面の［作り直す］（`remakeStale`）は `runPreset`（いまの条件をプリセットの重みに書き換える）をやめ、月の作り直しと同じく基準のプリセットの重みで解くだけ（`recreate(applyPreset(data.rules, 基準))`）。いまの条件で作った日が2日あるとき、1日を作り直すといまの条件が消え、もう1日が誤って「変わった」になっていたため
- `?do=recreate` を受けている間（`pendingRecreate`）は、どの日の自動作成も始めない（選んでいた日が今日と違うと、その日の自動作成が先に走っていた）
- 確かめ：`src/lib/runs.test.ts`・`src/lib/month.test.ts`（使い回しで presetId が書き直され消える）、`scripts/e2e-rebuild.cjs`（日の画面の［作り直す］でいまの条件が変わらず、ほかの日も増えない）

## 区切り5：急な欠勤・当日キャンセルを目立つ入口から登録して振り直す（追記。2026-10-18。PRD D167〜D172）

### 背景
監査（2026-10-18）で、急な欠勤・当日キャンセルという「その日の朝に急いでやること」ほど入口が見つけにくいと分かった。作り直す前に、今の流れをすべて洗い出した。

### 選択肢

### 決定

### 理由とトレードオフ
- 得るもの：その日の朝にやることが、日の画面の1つのボタンとホームの1枚のカードから、迷わず「起きたこと → 人 → 影響 → 振り直し → 確定」と進む。どこまで済んだかが段階の表示で分かる。案の無い日・列の無い人でも欠勤を登録できる。計算・契約・保存データは増えない（欄の状態は画面の中だけ）。今の差の欄・左下の帯・列の見出しの近道・連絡の一覧はそのまま残るので、慣れた人の動きは変わらない

## 区切り6：言葉と案内（点数の理由・用語・空の画面・凡例）（追記。2026-10-18。PRD D173〜D177）

- 月の案B はマスの読み方（区切り6）を壊し、案C は今の問題が残る。ツアーの案B は幅ごとに指す先と動きが変わり、引き出しの inert・下のタブ・右の欄と重なって、手間に対して得るものが小さい。保存の案B はデータを書き出して別の人へ渡すと「見た」が移り、初期状態に戻すたびに出るなど、人の状態とデータが混ざる

## 追加の区切り：右の欄の確定のボタンの帯を内容に付いてこさせる（追記。2026-10-18。PRD D194〜D197）

### 背景
利用者の要望（2026-10-18）「右側に出てくる欄（ダイアログ）の確定系のボタンが、画面いっぱいで一番下にあって、内容から離れている。近づけた方がよいか」→ 近づける方針で合意。
- 右の欄（`SidePanel`）は `.drawer`（縦の flex・高さ 100%）の中に 見出し・`.drawer-body`（flex: 1・巻く）・`.drawer-foot`（いつも一番下）の3つ。中身が短い欄（欠勤・キャンセルの1段目・月の「まとめて作る」・訪問を取り消す など）では、内容とボタンの間が画面の高さの半分ほど空く
- 欄ごとの上書きが2つあった：`plan.css` の `.drawer:has(.sudden-panel) .drawer-foot`（折り返し）と、600px 以下で欠勤・キャンセルの欄のボタンを全部全幅で縦に積む決まり。ほかの欄は狭い画面でも左寄せの横並びで、欄によって並びがばらばら
- スマホでは、入力中にキーボードが出ると、下に固定した帯がキーボードの裏に隠れる（欄は `position: fixed; inset: 0` で、キーボードは layout viewport を縮めない）。知らせ（トースト）は画面の下から 96px に出るので、帯と重なることがあった
- 制約：部品1か所で全部の欄に効かせる（`grep -rn SidePanel src` で13ファイル・16か所）。フォーカス（最初・戻す・Tab が回る）・inert・裏を巻かない・区切り4の `scroll-padding-top`・印刷を変えない。DemoData・契約は変えない

### 選択肢
1. 案A：帯を巻く領域の中で内容のすぐ後ろに置き、`position: sticky; bottom: 0`。短ければ内容の直後、長ければ欄の下に貼り付く。区切りは貼り付いている間だけ（IntersectionObserver の番兵）
2. 案B：`.drawer` の高さを中身に合わせる（`height: auto; max-height: 100%`）。帯は今の作りのまま欄の下。欄そのものが短くなり、背景（暗い幕）が欄の下に見える
3. 案C：帯をやめ、確定のボタンを各欄の内容の最後に置く（14か所を直す。長い欄では巻かないと届かない）
4. 区切りの出し方：(a) IntersectionObserver の番兵（帯のすぐ後ろの高さ0の要素が見えているか）、(b) CSS だけ（`animation-timeline: scroll()` のスクロール連動のアニメーション。Safari・Firefox で揃わない）、(c) 背景の `background-attachment: local` の影（帯の上に影を出せない）

### 決定
- 案A ＋ 区切りは (a)。`SidePanel` の中を `.drawer-body`（巻く）＞ `.drawer-content.stack`（内容）・`footer.drawer-foot`（sticky）・`.drawer-foot-end`（番兵）にする。`components/usePanelFoot.ts` の `usePanelFoot` が番兵を見て帯の `data-stuck`（"true"＝内容が帯の下に隠れている）を書き、CSS はそのときだけ背景（`--soft`）・上の線・上向きの影を出す。貼り付いていない間は欄と同じ背景で線を透明にする（位置がずれないよう線の幅は残す）
- 帯の高さは ResizeObserver で `.drawer-body` の `--drawer-foot-h` に入れ、`scroll-padding-bottom` にする（Tab で入った入力欄が帯の裏に隠れない。区切り4の html の `scroll-padding-top` とは別の要素なので重ならない）
- 狭い画面（600px 以下）の並びは CSS の `:has()` で決める：`.btn` が2つまでは同じ幅で横に（高さもそろえる）、3つ以上は先頭（主ボタン）を全幅・残りは2つずつ、ボタンでない子（誤り・注記）は1行。帯のある欄（14か所）はどれも主ボタンを DOM の先頭に置いているので、`order` で見た目だけ入れ替えることはしない（読み上げ・Tab の順と見た目を揃える）。欠勤・キャンセルの欄だけの上書き（`plan.css` の2つ）は消した。印刷の `body:has(.contact-sheet) .drawer-foot` は残す（今の決まりのまま帯を出さない）
- safe-area：帯の下は `12px + env(safe-area-inset-bottom)`、左右は `env(safe-area-inset-left/right)` を避ける。欄（z-index 1100）は下のタブ（950）より前なので、タブには隠れない
- キーボード：`useVisualViewportFit` が visualViewport の resize・scroll で、欄の入れ物（`.drawer-wrap`）の上端と高さを見えている所に合わせる。合わせるかどうかは `lib/panelFit.ts` の `panelFit`（純粋関数。差が 80px 未満（アドレスバー）・指で拡大中は合わせない）
- 知らせ：欄が開いている間（`body:has(.drawer-wrap)`）は、トーストを下の帯に重ねない（置き場所は下の「レビュー（PR #46）で直したこと」）

### 理由とトレードオフ
- 得るもの：短い欄はボタンが内容のすぐ下にあり、読み終えた所で押せる。長い欄は今と同じく巻かずに届き、内容が隠れている間だけ区切りが見えるので「まだ下に続く」が分かる。部品1か所なので全部の欄が同じ動き。狭い画面の並びが全部の欄で揃い、2つのボタン（保存・取り消し など）が1行に収まって縦に長くならない。入力中も確定のボタンが見える
- 失うもの：番兵と ResizeObserver の小さな JS が要る（IntersectionObserver が無い古いブラウザでは区切りを出さないだけで、位置は CSS で決まる）。狭い画面の2つ並びは文が長いボタン（「次へ：影響を見る」など）が2行になることがある。欄が開いている間の知らせは画面の上に出るので、見出しの下の段階の表示などに一時的に重なる。visualViewport の合わせ方は本物のキーボードでは e2e で確かめられない（e2e は visualViewport を差し替えて確かめる）
- 案B は短い欄で欄の下に幕が見え、右から出る引き出しの形が崩れる。案C は14か所を直し、長い欄で巻かないと届かない（今より悪い）。区切りの (b) はブラウザで揃わず、(c) は帯の上に影を出せない

### 影響
- 画面：`components/ui.tsx`（`SidePanel` の中の作り）・`components/usePanelFoot.ts`（新：`usePanelFoot`・`useVisualViewportFit`）・`lib/panelFit.ts`（新）・`styles.css`（`.drawer-body`・`.drawer-content`・`.drawer-foot`・600px 以下の並び・欄が開いている間のトースト）・`pages/plan.css`（欠勤・キャンセルの欄だけの上書きを消す）。各画面の欄（16か所）は直さない。DemoData・契約（`src/contracts/`）・データの版は変えない
- 確かめ：`src/lib/panelFit.test.ts`、`scripts/e2e-panel-foot.cjs`（新：1400px・390px で、欠勤・キャンセルの1〜4段目とキャンセルの2・3段目・〈スタッフ〉の閲覧（帯なし）と編集・月の「まとめて作る」・日の差の欄の「連絡の一覧」。短い欄は帯が内容のすぐ下で欄の下端より上・区切りなし、長い欄は貼り付き・途中まで巻いても見える・巻き終えると内容のすぐ下で区切りを消す、Tab で帯の裏の入力欄が隠れない、Tab が回る・Esc で戻る・裏を巻かない、390px の並び（2つは横に同じ幅で主ボタンが左、3つ以上は主ボタンを全幅、横にはみ出さない、タブに隠れない）・safe-area・キーボード（visualViewport を差し替え）、印刷）。既存の e2e（17本）は帯の位置に頼る確かめが無く、そのまま通る
- 対象外の確認（同じ考え方で見た。直していない）：中央の確認ダイアログ（区切り1b）と案内ツアーは、ボタンがカードの内容のすぐ下にあり同じ問題は無い。コマンドパレットはボタンの帯が無い。ただしスマホで入力中にキーボードが出ると、パレットの候補の下の方がキーボードの裏に入りうる（候補は巻けば見える。本物の端末では確かめていない）
- 見直す条件：欄の中にさらに下に貼り付く物（地図など）を置くときは、帯と重ならないか確かめる。2つ並びで2行になるボタンが多いという声があれば、ボタンの文を短くする

## 追記（2026-10-19。PRD D201〜D204）

### 背景
- 利用者の要望（2026-10-19）。月の要対応は押すとどの種類でも日の画面の先頭が開くだけで、入らない訪問は自分で巻いて探し、休みの人に残る訪問は「欠勤・キャンセル」を押し直し、拘束の上限超えは稼働の見込みを開いて月と人を選び直していた
- 稼働の見込みの日ごとの表の日付・〈スタッフ〉×日の表のマス、稼働時間の右の欄（「欠勤の登録・取り消しは予定の画面で」と文で案内するだけ）、空き状況の右の欄の日ごとの結果（「N人：名前、名前」）も行き止まりで、次に見る画面をメニューから開き直していた

### 決定
- 行き先は純粋関数 `lib/links.ts` で決める（`attentionTarget`・`suddenHref`・`unassignedHref`・`workloadHref`）。行き先は今ある URL の形（日の画面・`?do=absence`・稼働の見込みの `?ym=`・`?staff=`）を使い、足したのは日の画面の2つだけ：
  - `?date=…&do=unassigned`：その日を選び、案ができたら「入らなかった訪問」の列へ巻く（帯の「見る」の `goToNone` と同じ）。`?do=absence`・`?do=recreate` と同じく読んだら `?date=`・`?do=` を消す（戻るで繰り返さない）。`?do=` なので案内ツアーも出ない（D192）。入らない訪問が無くなっていれば巻かない
  - `?do=absence&staff=…`：その人の2段目（列の見出しの「欠勤を直す」と同じ `{ kind: 'staff', staffId }`）で開く。知らない人・その日に働かない人（稼働時間帯が無い＝「休む人」の選択肢 `staffChoices` に出ない人）なら1段目（PR #48 のレビュー）。`staff=` も読んだら消す
- 月の要対応（D201）：入らない訪問 → 日の画面の「入らなかった訪問」、休みの人に訪問 → その日の「欠勤・キャンセル」の欄（1段目。行には誰が休むかが無いので選ばせる）、拘束が上限を超える → 稼働の見込みをその月・先頭の人で（要対応の項目に人の id `staffIds` を足した。名前の並びと同じ順）、そのほか（条件が変わった・欠勤がある）→ 今のまま日の画面。行全体が1つのボタンのまま（入れ子にしない）で、行の下に「（〜で開く）」を添える。移る前に選んでいる日付をその日にする
- 稼働の見込み（D202）：日ごとの表の日付をボタンにして日の画面へ。〈スタッフ〉×日の表のマスは押しても何も起きなかった（title の内訳だけ）ので、マスをボタンにして日の画面へ（見た目はマスのまま・title は今どおり・読み上げは見えている数字（例「2.5!」）を先頭に内訳＋「（日の画面で開く）」）。表の下の説明は、タッチでは指を置いても内訳が出ないので「内訳は下の「日ごと」の表で見られます」にした（PR #48 のレビュー）。名前の吹き出しは付けない（D124）
- 稼働時間の右の欄（D203）：「この日の欠勤を登録する」（欠勤があれば「直す・取り消す」）のリンク（`<Link>`。Ctrl+クリックで新しいタブでも開ける）。その日に働く日（保存した時間帯があり、最終勤務日の後でない）だけ出す。押しても `setDate` しない（日の画面が `?date=` を読むので要らず、Ctrl+クリックで元のタブの日付まで変わるため）。主ボタンは「この時間で保存」のまま
- 空き状況の右の欄（D204）：日付ごとに「その日の案を見る」（`<Link to="/plan?date=…">`。ふつうに押すと同じタブで移り、Ctrl+クリック・中クリックで新しいタブ。読み上げは見えている文字が先頭）。日の画面は `?date=` だけのときもその日を選んで `?date=` を消すようにした（`?do=` があるときはそれぞれが読む）。名前の吹き出しは付けない（D124）
- 日付の受け渡し：ボタンで移る所は今のやり方（`setDate` してから `navigate('/plan')`）、リンク（`<Link>`）は URL の `?date=` を日の画面が読む（リンクの側で `setDate` しない）。日付は日本時間（`jstDate`）
- `?do=unassigned` の待ち方（PR #48 のレビュー）：その日に着いた時点で案が無ければ、自動作成を始めたとき（`autoTried` に入れたとき）だけ作り終わるのを待つ。自動作成が走らない（その画面で一度試した日・作っている途中でもない）・作れなかったときは忘れる（あとで「AI案を作る」を押したときに急に巻かない）。作っている途中には `batch` も数える

### 採らなかった案
- `?focus=unassigned` のような別の名前の値：`?do=` と同じ「操作の欄・場所を開く一時の値」で、ツアーを出さない判定（`?do=` があるか）や消し方をそのまま使えるので `?do=unassigned` にした
- 休みの人に残る訪問から、休む人を選んだ2段目で開く：要対応の行は件数だけで人を持たず、2人以上のこともあるので1段目にした（人が分かる稼働時間の右の欄は2段目）
- 拘束の上限超えから日の画面を開く：日の画面には拘束の数字が無く、人ごとの日ごとの長さを見るのは稼働の見込みなので、稼働の見込みにした（2人以上なら先頭の人。ほかの人は日ごとの選択で切り替える）
- 行の中に別のリンクを足す（例：行の右に「稼働の見込み」）：ボタンの入れ子になり、行のどこを押すと何が起きるかが分かれる
- 空き状況から日の画面をいつも新しいタブで開く：ほかの画面へ移る所はどこも同じタブなので、ふつうに押したときは同じタブにした。空き状況の入力は画面の中の状態で戻ると初めの入力に戻るので、残したいときは Ctrl+クリック・中クリックで新しいタブに開ける（リンクにした。PR #48 のレビュー）
