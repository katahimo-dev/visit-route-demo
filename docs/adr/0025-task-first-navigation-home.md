# ADR-0025：UI/UX 改善：やりたいことから入る導線（ホーム「今日やること」はその第1弾）

- 日付：2026-10-18
- 状態：採用（利用者の依頼（2026-10-18）「直感的にやりたいことが操作できるように」。第1弾のホームは PRD D141〜D145。区切り2の進み具合の帯は PRD D151〜D155（下の追記）。ほかの区切りは予定）

## 背景
画面の監査（2026-10-18）で、やりたいことに届くまでの迷いが分かった。

- 起動すると案内なしでいきなり日の画面（`#/plan`）になる。今月の準備がどこまで進んでいるか、次に何をすればよいかは、月の画面の「今月の準備」（PRD D59）を開かないと分からない
- メニューは「データの種類」（〈利用者さん〉／〈スタッフ〉／割当の設定）で並ぶ。やりたいこと（月を組む・欠勤に対応する・問い合わせに答える）とは合っていない
- 同じ操作が複数か所にある（案を作る＝月の見出しのボタン・今月の準備の②・日の「案を変える▾」。確定＝日と月の③）。逆に「急な欠勤」は列の見出しの小さいボタンで見つけにくい
- 制約：新しい保存データを増やさない（データの版・Excel・JSON の書き出しを変えない）。データを書き換えるのは store だけ。既存の画面の URL・e2e を壊さない。スマホは表示の確認が主（PRD §7）

## 選択肢
1. 案A：起動したときの画面に「ホーム（今日やること）」を足し、今の状態から次の一手をカードで出す。カードは既存の画面・既存の操作（月のまとめて作るの欄・右の欄、日の画面）へ移るだけ。判定は純粋関数で、月の画面と同じ数え方
2. 案B：日の画面の上に「今日やること」の帯を足す（起動は今のまま日の画面）
3. 案C：メニューを先にやりたいこと順に並べ替える（ホームは作らない）
4. 案D：最初にツアー（案内の吹き出し）を出す

## 決定
案A。決まりは `lib/home.ts`（純粋関数）の1か所：見る月 `homeMonths`（今月。残り7日以下なら来月も）・見る日 `homeDays`・カード `homeTasks`（要対応 → 今日の予定 → 確定していない日 → 案を作る）。日の状態は月の画面の計算を `lib/useDayStatuses.ts` に切り出して共通に使う（要対応・確定の件数が月の画面と食い違わない）。月の画面の操作は `?do=batch|attention|unconfirmed` で開き、1回行ったら URL から消す。起動（`#/`）と知らない URL の行き先をホームに。メニューの先頭とスマホの下のタブ（5つ）に「ホーム」。

## 理由とトレードオフ
- 得るもの：開いた人が1画面で「次に何をするか」が分かり、1クリックでその操作の画面に着く。新しい保存データが無いので、データの版・書き出し・移行は変わらない。月の画面と同じ数え方なので数字が食い違わない。カードの行き先は既存の操作なので、機能を二重に作らない
- 失うもの：起動のたびに今月（月末は来月も）の日を compile・採点する（月の画面と同じ重さ。8人・約17件／日の一月で 500ms 以内）。起動しても日の画面を開かないので、今日の案の自動作成（PRD D52）は今日のカードを押したときになる。スマホの下のタブが5つになり、1つの幅が狭くなる（390px で78px）
- 案B は日の画面がさらに長くなり、月の準備（来月の訪問を作る）が日の画面の話でなくなる。案C は並べ替えだけでは「今の状態」が分からない（第7弾で別にやる）。案D は一度見たら終わりで、毎日の「次の一手」にならない（第8弾の初回ツアーで補う）

## 影響
- 画面：`pages/HomePage`（`home.css`）、`app/App.tsx`（ルート `/home`・`*` の行き先・メニューの先頭）、`lib/nav.ts`（`BOTTOM_TABS` に `/home`）、`styles.css`（下のタブを5列）、`pages/MonthPage`（`?do=` と、日の状態の計算を `lib/useDayStatuses` へ移す。見た目は変えない）。データ・契約（`src/contracts/`）・store は変えない
- 確かめ：`src/lib/home.test.ts`（何も無い・全部済み・一部済み・月末）、`scripts/e2e-home.cjs`、`scripts/e2e-mobile.cjs`（下のタブ5つ）
- 見直す条件：カードが多すぎる（月ごとに3枚×2か月）という声があれば、月ごとのカードを1枚にまとめる。起動の重さが気になる事業所（数十人・日に数十件）では、ホームは今月の今日から2週間だけ見るかを決める

## レビュー（PR #36）で直したこと（追記）
- 確定していない日の数え方：ホームは案のある日（未確定・未確定の変更あり）だけ数えていたため、月の「今月の準備」の③・右の欄（訪問があって確定済みでない日。案の無い日も含む）と日数がずれた（ホームで2日、開いた欄には5日）。ホームを月の画面に合わせ、同じ日数・同じ並びにした。案の無い日は「案をまとめて作る」のカードにも出る（重なってよい）。月の③の意味は変えない
- `?do=batch`：この月に訪問が無いときだけでなく、まだ案の無い日の対象が0日のときも欄を開かない（見出しのボタンの欄を開いても「作り始める」が押せないため）
- ホームは `useDayModel(今日)` をやめ、compile が読むデータだけを取る `useCompileInput` を使う（今日の問題を二重に compile しない）

## 区切り2：予定に共通の進み具合の帯（追記。2026-10-18。PRD D151〜D155）

### 背景
案を作る入口が3か所（月の見出しの「◯月の案をまとめて作る」・月の「今月の準備」の②「まとめて作る」・日の「案を変える▾」）、確定が2か所（日の「この割当で確定」・月の③）にあった。月の画面では同じ数字（案のある日・確定した日）が「今月の準備」と見出しの要約に並び、週・日の画面では今月がどこまで済んだか・次に何をするかが分からなかった。

### 選択肢
1. 案A：月・週・日の見出しの下に同じ形の細い帯（見ている月の今日以降の 訪問・案・確定・要対応＋次の一手のボタン1つ）を置き、月の「今月の準備」（①〜③）と見出しの主ボタンを帯にまとめる。「訪問だけ作る」はまとめて作るの欄の中へ
2. 案B：帯は足すが「今月の準備」は残し、役割を分ける（帯＝要約と次の一手、今月の準備＝①〜③の操作のボタン）
3. 案C：週・日には帯を置かず、［月｜週｜日］の「月」に件数のバッジを付ける

### 決定
案A。決まりは `lib/progressBand.ts`（純粋関数）：次の一手 `bandNext`（作っていない訪問・案の無い日 → まとめて作る、手当てが要る要対応 → 要対応を見る、確定していない日 → 確定していない日を見る、見るだけの要対応 → 要対応を見る、無ければ済み）・`urgentCount`・見る月 `bandMonth`（選んでいる日付の月。週は週の中の選んでいる日の月）・移る先 `bandHref`（月の画面の `?do=`）。見た目は `components/progressBand.tsx` の `ProgressBand`（月の画面は自分で数えた値を渡して主ボタン、欄は画面の中で開く）と `ScheduleBand`（週・日。`useDayStatuses`・`monthProgress`・`attentionList` で数える）。月の画面の `?do=batch` は、まだ案の無い日が無ければ「確定していない日をすべて作り直す」で開く（D143 を直す）。

### 理由とトレードオフ
- 得るもの：どの予定の画面でも同じ場所・同じ数で「今どこまで済んだか」と「次の1つ」が分かる。数え方は月の画面・ホームと同じ部品（`useDayStatuses`・`monthProgress`）なので食い違わない。月の画面の「まとめて作る」は帯の1か所になり、同じ数字が2か所に並ばない。新しい保存データ・契約は無い
- 失うもの：月の画面の「今月の準備」の①〜③の段の並び（手順の見せ方）と、D80 の凡例つきの積み上げが無くなる（帯の下の縁の細い積み上げと、数字の✓で代える）。「訪問だけ作る」は欄を開かないと押せない（使う人は少なく、欄の中に「案は作らない」と書いて置く）。週・日の画面を開くと、その月の今日以降の案のある日を compile・採点する（月の画面と同じ重さ。`useDeferredValue` で画面を描いた後に回し、日ごとの覚えで手直しのたびに月全体を数え直さない。e2e で 3 秒以内・確定の操作は 1.5 秒以内を確かめる。手元では案が全部ある月で 100ms ほど）
- 案B は帯と今月の準備で同じ数字が2か所に並び、「まとめて作る」の入口も2か所のまま（今回の問題が残る）。案C は週・日で次の一手が押せない
- 帯の次の一手は月の画面だけ主ボタンにする。日の画面は「この割当で確定」が主ボタンなので、帯は普通のボタンにして主ボタンを1つ（多くて2つ）に保つ。日の確定は今のまま日の画面で行い、帯は「この日 未確定（「この割当で確定」で確定）」と状態を見せるだけ（確定の入口を増やさない）

### 影響
- 画面：`components/progressBand.tsx`（`progressBand.css`）を足す。`pages/MonthPage`（見出しのボタンと `MonthPrep`・`PrepStep` をやめ帯に。`openBatch` を帯と `?do=batch` で共通に。欄に「訪問だけ作る」）、`pages/WeekPage`・`pages/PlanPage`（見出しの下に `ScheduleBand`）。データ・契約（`src/contracts/`）・store は変えない。`components/glance` の `PrepBar`（今月の準備の積み上げ）は使う画面が無くなったので消す（色の CSS `.prep-bar`・`.prep-part` と `lib/glance` の `prepParts` は帯の積み上げで使う）
- 確かめ：`src/lib/progressBand.test.ts`、`scripts/e2e-progress.cjs`。`scripts/e2e-home.cjs` の「③の日数」は帯の確定していない日数で確かめる
- 見直す条件：帯の次の一手が「要対応を見る」のまま動かない（欠勤のある日は手当てを終えても要対応に残る）という声があれば、見るだけの要対応を次の一手から外す。週・日の帯が重いという事業所（数十人・日に数十件）では、帯を今日から2週間だけ数えるかを決める

### レビュー（PR #38）で直したこと（追記）
- 月の見出しの下の要約（月全体）が帯（今日以降）と同じ言葉「訪問」「案のある日」で違う数を並べていたので、要約は帯に無い「入らない・当日キャンセル」（月全体）だけにした
- 済んだ「案 ✓」から開いたとき、欄の既定が「確定していない日をすべて作り直す」（手直しを捨てうる操作）になっていた。既定はいつも「まだ案の無い日だけ」（0日でも）とし、作り直しは利用者が選んだときだけにした。欄を開かないのは、作っていない訪問・案の無い日・確定していない日がどれも無いときだけ
- 読み上げ：数字のリンクに押すと何が起きるかの aria-label、✓ の「済」、手当てが要る要対応の「要手当て」。aria-live の領域は最初から空で置き、数え直して変わったときだけ中身を入れる（開いたときには読まない）
- Ctrl・⌘・Shift・中ボタンのクリックは横取りせずブラウザに任せる（新しいタブで月の画面）
- 週・日の帯の定期パターンの展開は、読むもの（定期パターン・訪問・〈利用者さん〉）と月で覚え（`lib/month` の `expandMonthVisits`）、案の手直し・確定のたびに月全体を展開し直さない
- `scripts/e2e-home.cjs` は月末7日以内（来月のカードも並ぶ）と、今月の残りが今日だけ（カードが日の画面へ移る）でも通るようにした。`scripts/e2e-progress.cjs` も同じ日付で通す

## これからの区切り（予定。1区切り＝1PR。着手のときにこの ADR に追記する）
1b. （利用者の追加要望（2026-10-18）で差し込み。済み）ブラウザ標準の確認（confirm）を、画面の中央に出す独自の確認ダイアログに置き換える。判断が独立しているので ADR-0026 に書いた（PRD D146〜D150）
2. （済み。上の追記。PRD D151〜D155）予定（月・週・日）に共通の進み具合の帯（作成済 x/y・確定 x/y・要対応）を置き、「まとめて作る」の重複をなくす
3. 日の「案を変える▾」の中身を目的の言葉に（もう一度作らせる／少し良くする／2つの案を比べる／元に戻す）。比較は案が1つでも「もう1案作って比べる」
4. 条件（重み・相性・稼働時間など）を変えたら「影響する日 N日 →［作り直す］［後で］」の帯をどの画面でも出す
5. 急な欠勤を目立つ入口に（日の画面のボタン、人を選ぶ → 振り直し案 → 確定 の段階）
6. 言葉と案内：点数の理由を一言、用語の言い換え・説明、空の画面に「なぜ空か＋次の一手」、凡例を畳む
7. メニューを用途ごとに並べ替え・名前を区別し、コマンドパレット（Ctrl+K）
8. 個別：空き状況の段階化、週の切替を1つに、スマホ（月の一覧表示・地図ボタンの重なり）、データのファイル選択を日本語に、初回ツアー
