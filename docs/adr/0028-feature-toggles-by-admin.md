# ADR-0028：管理者設定で機能を入り切りし、事業所に要る機能だけの画面にする（機能の入り切り）

- 日付：2026-10-19
- 状態：提案（利用者の依頼（2026-10-19）「ヒアリング結果をもとに機能拡張したが、それぞれにとって過剰な機能がある。管理者設定で ON/OFF して必要な機能のみのすっきりした画面にしたい」。§「決めてほしいこと」を利用者が決めたら採用にし、PRD・design.md に書く）

## 背景
- 2社のヒアリング（訪問介護・移動支援 株式会社アルカ様 2026-09-24／訪問看護 キュアオール様 2026-10-15）を受けて、第1弾〜第3弾（ADR-0013〜0015）と、メール・道順・住所検索・Excel の名簿など（ADR-0016〜0020）を足した。画面は16、メニューの項目は16になった
- 2社で要る機能が違う
  - アルカ様（8人・約20名・直行直帰・毎週固定）：当日キャンセル・欠勤の振り直し、拘束・交通費の見込み、退職者の担当替え、段階（相談受付→契約→利用中）と紹介元。相性は「最初は性別・距離・稼働制約の3軸で十分」
  - キュアオール様（約69名・訪問看護）：第N曜日・曜日ごとの時刻、入院などの〈利用者さん〉の休み、鍵・駐車場の決まりごと、空き状況と案内文（ケアマネへの即答）、担当を限る（特定の2名）、希望休のまとめ入力、月の印刷（紙のカレンダーの代わり）
  - 相手の業務に無い機能（例：アルカ様に月の印刷・空き枠の案内文、キュアオール様に稼働の見込み・段階）がメニュー・画面の欄・ボタンに並び、画面が重い
- 今の作り（調査 2026-10-19）
  - 機能の入り切り・業種での分かれ道は無い。`org.industry` は Excel の入出力でしか使っていない。事業所ごとに変えられるのは呼び方（`org.terms`）と、値が0なら出さない交通費（`fareYenPerKm`）・拘束の上限（`spanLimitHours`）だけ
  - メニューは `lib/nav.ts` の `menuSections` の1か所から、左のメニュー・引き出し・下のタブ・上の帯の名前・コマンドパレットの画面が引く。一方、ルート（`app/App.tsx`）・パレットの操作（`lib/commandPalette.ts`）・ホームのカード（`lib/home.ts`）・案内ツアー（`lib/tour.ts`）・画面の中の入口（〈利用者さん〉の欄の定期パターン・休み、月の印刷のボタン、週のメール、行き止まりから移るリンク `lib/links.ts` など）は、それぞれ URL を直書きしている
- 制約：ログインは作らない（PRD §4。1ブラウザ＝1事業所）。データの版は1のまま（欠けた項目は zod の既定値で補う今の方式）。外部送信は増やさない。機能を消してもデータは消さない（入り直せば戻る）

## 選択肢
### 入り切りの単位
1. 案A：画面の単位（16の画面を出す・出さない）
2. 案B：機能の単位（約20。画面より細かく、画面の中の欄・ボタン・リンクも含めて1つの名前で入り切りする。下の「機能の一覧」）
3. 案C：業種のひな形だけ（訪問介護／訪問看護／すべて を選ぶだけで、個別には切らない）

### 設定の持ち方
1. 案A：`org.features`（機能の ID → 入・切）を DemoData に持つ。無い ID は一覧の既定（すべて入）。JSON の控えと一緒に渡る
2. 案B：DemoData と別の localStorage のキー（案内ツアーの「見た」と同じ。ADR-0025 追記）。控え・初期状態に戻すに入らない

### ひな形（すぐ使える組み合わせ）
1. 案A：「ひな形を当てる」ボタンで、その時の入・切を一度だけ書き込む（あとから個別に直せる。業種 `org.industry` とは連動しない）
2. 案B：業種を選ぶと自動で入・切が決まり、個別の直しは差分として持つ

### 切った機能の割当への効き方（相性・担当を限る・希望休・〈利用者さん〉の休み のように AI案に効くもの）
1. 案A：画面から隠すだけ。入っているデータは今までどおり AI案に効く
2. 案B：画面から隠し、AI案の計算（`matching` の compile）からも外す。データは残す（入り直せば効く）

## 推奨
- 単位は案B（機能の単位）＋ ひな形は案A（当てるボタン）。案A（画面の単位）では「欠勤・キャンセル」「メール」「道順のリンク」「月の印刷」のように画面の中の欄・ボタンが切れず、すっきりしない。案C は事業所ごとの細かい違い（例：アルカ様も空き状況は B 優先で要る）を表せない
- 持ち方は案A（`org.features`）。控え（JSON）で他の端末・人へ設定ごと渡せる。版は1のまま、無い古いデータは既定（すべて入）で読むので、今の画面は何も変わらない
- 効き方は案B（計算からも外す）。隠れた設定が AI案に効き「なぜこの担当か」（D12）に見えない条件が出ると、管理者が理由を言い直せない（PRD §5 の AI案の納得感）。そのため matching は「切った機能の条件を読まない」ことを契約に書き、記録の問題のキー（`AiRun.inputKey`）に入り切りを含める（入り切りを変えたら「条件が変わった」＝ D161 の作り直しの帯に乗る）

## 仕組み（推奨の案で作るとき）
- 契約：`src/contracts/features.ts` に機能の ID の一覧（`FEATURE_IDS`）と `featuresSchema`（ID → boolean の部分的な表。知らない ID は捨てる）。`orgSchema` に `features: featuresSchema.default({})`。無い ID は「入」。版は1のまま
- 機能の一覧の正は1か所：`lib/features.ts` に、機能ごとの名前・説明・グループ・依存・その機能の URL（ルート・`?do=`）・ひな形の入・切を持つ純粋関数の表。`isOn(features, id)` は依存を見る（`vacancy` が切なら `vacancyNotice` も切）
- 画面への渡し方：`useFeature(id)`（store の `org.features` を読むだけ）と、入口を囲む `<Feature id>`。データを書き換えるのは今どおり store の `update(fn)` だけ
- 出し分けの場所（URL の直書きを `lib/features.ts` の表に寄せる）
  - メニュー：`menuSections(terms, today, features)`。下のタブ・上の帯の名前・パレットの画面は今どおりここから引くので自動で消える
  - ルート：切った機能の URL を開くとホームへ移し「この機能は設定で切っています（設定を開く）」と知らせる（ブックマーク・古いリンク・`?do=` 対策）
  - パレットの操作・ホームのカード・案内ツアーの枚・行き止まりから移るリンク（`lib/links.ts`）：表から引き、切った機能の行き先を出さない
  - 画面の中の欄・ボタン：`<Feature id>` で囲む
- 計算（効き方の案B）：matching の compile に入り切りを渡し、切った機能の条件（相性・担当を限る・〈利用者さん〉の休み・希望休のメモ）を読まない。`AiRun.inputKey` に入り切りを含める。solver・evaluate は compile の出力だけを見るので変えない
- 設定の画面：`#/settings`「機能の設定」。メニューの最後のグループを「設定・データ」にして「データ」と並べる。上にひな形の3つ（当てる前に独自の確認ダイアログで差を出す）、下にグループごとのスイッチ（名前・1行の説明・依存の注記・切ると隠れるもの）。設定の画面と土台の画面は切れないので、戻れなくなることは無い
- 呼び方（`org.terms`）・交通費・拘束の上限の欄も、この設定の画面へ寄せるかは別に決める（今はデータの画面・稼働の見込みの画面）
- Excel：「事業所」シートに機能の行を足すかは別に決める（初回は JSON の控えだけで渡る）

## 理由とトレードオフ
- 得るもの：事業所ごとに要る機能だけのメニュー・画面になる（アルカ様型でメニューの項目 16 → 13、キュアオール様型で 16 → 12 の見込み）。ひな形で最初の設定が1手。データを消さないので試しに切っても戻せる。今のデータ・URL・初期状態は「すべて入」で何も変わらない。デモで「どの機能を切ったか」が要件の材料になる（PRD §1 の目的）
- 失うもの：入り切りの組み合わせが増え、確かめる範囲が広がる（機能ごとの e2e は「すべて入」と2つのひな形の3通りに絞る）。URL の直書きを表に寄せる作り直しが要る（App・nav・commandPalette・home・tour・links）。切った機能の条件が AI案から外れるので、切り替えると案が変わる（作り直しの帯で知らせる）。ログインが無いので、だれでも設定を戻せる（1ブラウザ1事業所の前提のまま。鍵は付けない）

## 決めてほしいこと
1. 切った機能の割当への効き方：案B（計算からも外す。推奨）か 案A（隠すだけ）か
2. 「条件の重みとプリセット」「案を比べる」を2つのひな形で切ってよいか（デモの目的2「割当の条件を柔軟に試す」の入口を隠すことになる。推奨は「ひな形では切る・すべてでは入」で、条件を試したい人は設定で入れる）
3. ひな形の入・切の表（上）の見立てでよいか
4. 設定の画面を新しく `#/settings` にするか（推奨）、データの画面の中に置くか

## 影響
- PRD：§3 に要件（D210〜）、§4 に「ログイン・権限で設定を守る・利用者ごとの表示の違い・機能ごとの料金」はやらないを足す
- design.md：§4 に features（`lib/features.ts`）と各コンポーネントの出し分け、§5 に `org.features` の契約と matching の「切った機能の条件を読まない」
- store：`org.features` の既定値だけ（repair は知らない ID を捨てる）。版は1のまま
- テスト：機能の表の整合（メニュー・パレット・ホーム・ツアー・links の行き先がすべて表のどれかか土台に属する）、依存、compile の入り切り、e2e は `scripts/e2e-features.cjs`（3通り × メニュー・ルートの移し先・画面の中の入口）
- 見直す条件：デモでほぼ全員が同じ機能を切る → その機能の既定を「切」に／1つの機能の中で一部だけ要る声が多い → 機能を分ける
