# ADR-0028：管理者設定で機能を入り切りし、事業所に要る機能だけの画面にする（機能の入り切り）

- 状態：採用（2026-10-19）
- 関連：PRD D210〜D216、ADR-0013〜0020（切る対象の機能）、ADR-0025・0027（メニュー・パレット）

## 背景
2つのヒアリング（訪問介護・移動支援の事業所／訪問看護事業所）を受けて、第1〜3弾（ADR-0013〜0015）とメール・道順・住所検索・Excel の名簿など（ADR-0016〜0020）を足し、画面もメニューの項目も16になった。事業所によって要る機能が違う。
- 訪問介護・移動支援（8人・約20名・直行直帰・毎週固定）：当日キャンセル・欠勤の振り直し、拘束・交通費の見込み、退職者の担当替え、段階と紹介元。相性は最初は3軸で十分
- 訪問看護（約69名）：第N曜日・曜日ごとの時刻、〈利用者さん〉の休み、鍵・駐車場の決まりごと、空き状況と案内文、担当を限る、希望休のまとめ入力、月の印刷
- 相手の業務に無い機能がメニュー・欄・ボタンに並んで画面が重く、ほかの法人に提案するときも同じことが起きる。利用者の依頼は「管理者設定で ON/OFF して、必要な機能だけのすっきりした画面に」「ひな形は法人名を出さず機能的な名称に」

調査（2026-10-19）：機能の入り切りも業種での分かれ道も無い（`org.industry` は Excel の入出力でしか使っていない）。メニューは `lib/nav.ts` の1か所から引くが、ルート・パレットの操作・ホームのカード・案内ツアー・画面の中の入口・`lib/links.ts` は URL を直書きしている。
制約：ログインは作らない（PRD §4。1ブラウザ＝1事業所）。データの版は1のまま（欠けた項目は zod の既定値）。外部送信は増やさない。機能を切ってもデータは消さない（入り直せば戻る）。

## 決定
機能の単位（約20）で入り切りし、設定は `org.features` に持つ。ひな形は「当てる」ボタン。切った好み・決まりは計算からも外し、事実は効かせ続ける。管理者設定は新しい画面 `#/settings` で、鍵・ログインなしでだれでも開ける（デモなので利用者が了承）。

- 持ち方：`src/contracts/features.ts` に機能 ID の一覧（`FEATURE_IDS`）と `featuresSchema`（ID → boolean の部分表。知らない ID は捨てる）。`orgSchema.features`（既定 `{}`）。無い ID は「入」なので今の画面は何も変わらない。JSON の控えで他の端末・人へ設定ごと渡せる。repair は知らない ID を捨てる
- 機能の一覧の正は1か所 `lib/features.ts`（名前・説明・グループ・依存・URL（ルート・`?do=`）・ひな形の入切の純粋関数の表。`isOn` は依存を見る）。画面へは `useFeature(id)` と `<Feature id>`。データを書き換えるのは今どおり store の `update(fn)` だけ
- 常に出す土台（切れない）：ホーム・月・週・日・〈利用者さん〉一覧・〈スタッフ〉一覧・稼働時間・訪問の種類・データ・設定
- 切れる機能（ID）：毎月の第N曜日・曜日ごとの時刻（`patternMonthly`）、〈利用者さん〉の休み（`clientLeave`）、希望休のまとめ入力（`requestedOff`）、月の予定の印刷（`monthPrint`）、案を比べる（`compare`）、欠勤・キャンセル（`sudden`。入口と欄だけ切り、すでに振り直した案の差の欄・連絡の一覧は残す）、空き状況（`vacancy`）、空き枠の案内文（`vacancyNotice`。`vacancy` に依存）、相性（`compat`）、担当を限る（`allowedStaff`）、段階・紹介元（`clientStage`。切ると利用中／終了の2つだけ選べる）、訪問先の決まりごと（`visitNotes`）、退職・担当替え（`offboard`）、稼働の見込み（`workload`）、交通費（`fare`。`workload` に依存）、条件の重みとプリセット（`rules`。切ると基準のプリセットだけで作る）、メール（`mail`）、道順のリンク（`mapsLink`）、郵便番号・住所の検索（`geocode`。地図のクリックで置くのは残る）、Excel の入出力（`excel`。控えの JSON は残る）。各機能が隠すもの（メニュー・欄・ボタン）の細部は design.md
- 出し分け：メニューは `menuSections(terms, today, features)` から（下のタブ・上の帯・パレットの画面も自動で消える）。ルートは、切った機能の URL（`?do=` 含む）を開くとホームへ移し（replace）「この機能は設定で切っています（設定を開く）」と閉じられる知らせを出す。パレットの操作・ホームのカード・ツアーの枚・行き先のリンク（`lib/links.ts`）は表から引き、切った機能の行き先を出さない。画面の中の欄・ボタンは `<Feature id>` で囲む。URL の直書きは表に寄せる
- 計算への効き方：切った好み・社内の決まり（相性（NG の×も外れる）・担当を限る）は matching の compile も読まない（隠れた設定が AI案に効き「なぜこの担当か」（D12）に見えない条件が出るのを避ける）。事実（〈利用者さん〉の休み・欠勤と希望休・最終勤務日・定期パターンの展開）は切っても効かせ続ける（外すと休みの人に訪問が入るため）。記録 `AiRun` に `calcFeatures` を残し、今と違えば「条件が変わった」（D43・D161）に含める。`problemKey` も変わる。solver・evaluate は変えない
- ひな形（法人名・ヒアリングの出典は画面に出さない。「当てる」は一度だけ書き込む出発点で、あとから個別に直せる。当てる前に独自の確認で差を出す。`org.industry` とは連動しない）：
  - 基本：予定・欠勤・キャンセル・空き状況・相性・道順のリンク・住所の検索だけ。初めて使う・少人数向け
  - 労務・契約管理：基本 ＋ 稼働の見込み・交通費・退職・担当替え・段階・紹介元。毎週固定の契約が中心で拘束・交通費・人の入れ替わりを見たい事業所向け
  - 月次予定・現場共有：基本 ＋ 第N曜日・曜日ごとの時刻・〈利用者さん〉の休み・希望休・月の印刷・空き枠の案内文・担当を限る・訪問先の決まりごと・Excel。利用者が多く月ごとの予定が複雑で、休み・担当の決まり・鍵や駐車場の情報を共有したい事業所向け
  - すべて：全部入（今のまま）。条件を試す・デモ・営業向け
  - 「条件の重みとプリセット」「案を比べる」「メール」は「すべて」だけが入（条件を試したい人は管理者設定で入れる）
- 設定の画面：メニューの最後のグループ「管理者」に「管理者設定」と「データ」。上にひな形4つ、下にグループごとのスイッチ（名前・1行の説明・依存の注記。依存先が切なら押せず理由を出す。押すとすぐ保存してトースト）。設定の画面と土台の画面は切れないので戻れなくなることはない
- 呼び方・交通費単価・拘束の上限の欄を設定の画面へ寄せるか、Excel の「事業所」シートに機能の行を足すかは別に決める（初回は JSON の控えだけで渡る）
- 確かめ方：機能の表の整合テスト（メニュー・パレット・ホーム・ツアー・links の行き先がすべて表か土台に属する）、依存、compile の入り切り、`scripts/e2e-features.cjs`（ひな形の4通り × メニュー・移し先・画面の中の入口）。画面・契約の細部は design.md

## 検討した案
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| 単位A：画面の単位（16画面） | 単純 | 欠勤・キャンセル・メール・道順・月の印刷のような画面の中の欄・ボタンが切れずすっきりしない | 不採用 |
| 単位B：機能の単位（約20） | 画面の中の入口まで1つの名前で切れる | 組み合わせが増え、URL の直書きを表に寄せる作り直しが要る | 採用 |
| 単位C：業種のひな形だけ（個別に切らない） | 最も簡単 | 事業所ごとの細かい違い（訪問介護も空き状況は要る等）を表せない | 不採用 |
| 持ち方A：`org.features`（DemoData） | 控えで設定ごと渡せる。版は1のまま | 初期状態に戻すと消える | 採用 |
| 持ち方B：別の localStorage キー | 控え・初期化に入らない | 他の端末・人へ渡せず、事業所の設定と人の状態が混ざる | 不採用 |
| ひな形A：「当てる」ボタンで一度だけ書き込む | 個別の直しが素直。業種と連動しない | 当てたあとの変更は自分で管理 | 採用 |
| ひな形B：業種で自動決定し個別の直しを差分で持つ | 業種を変えれば追従 | 状態が二重になり説明しにくい | 不採用 |
| 効き方A：画面から隠すだけ（データは AI案に効く） | 実装が軽い | 隠れた設定が AI案に効き、管理者が理由を言い直せない（PRD §5 の納得感） | 不採用 |
| 効き方B：好み・決まりは計算からも外す（データは残す） | 見えない条件が出ない。入り直せば効く | 切り替えると案が変わる（作り直しの帯で知らせる） | 採用 |

## 結果・トレードオフ・見直す条件
- 得るもの：事業所に要る機能だけのメニュー・画面になる（メニューの項目は 16 → 基本12・労務・契約管理13・月次予定・現場共有12の見込み。管理者設定の1つを除く）。ひな形で最初の設定が1手。データを消さないので試しに切っても戻せる。今のデータ・URL・初期状態は「すべて入」で何も変わらない。デモで「どの機能を切ったか」が要件の材料になる（PRD §1 の目的）
- 失うもの：
  - 入り切りの組み合わせが増え確かめる範囲が広がる（e2e はひな形の4通りに絞る）
  - 切った機能の条件が AI案から外れるので、切り替えると案が変わる（作り直しの帯で知らせる）
  - ログインが無いので、だれでも管理者設定を開いて戻せる（デモなので受け入れる。1ブラウザ1事業所の前提のまま、鍵は付けない）
- 見直す条件：デモでほぼ全員が同じ機能を切るならその機能の既定を「切」に。1つの機能の中で一部だけ要る声が多ければ機能を分ける
- 影響：PRD §3 に要件（D210〜）、§4 に「ログイン・権限で設定を守る・利用者ごとの表示の違い・機能ごとの料金」はやらないを追記
