# ADR-0031：月のまとめて確定と初期データの案

- 状態：採用（2026-10-19）
- 関連：PRD D223〜D226、ADR-0004（AI案を土台に手直し・固定）・0008（開いた日に案を作る）・0009（予定と AI案を1画面）・0012（まとめて作る）・0025（ホーム・進み具合の帯）・0026（独自の確認）

## 背景
AI案 → 手直し → 確定の流れのうち、最後の「確定」と最初の「AI案が見える」までが重い。
- 確定は日の画面の「この割当で確定」だけ（`manualPlans[date]` を書くのはここだけ）。一月を確定するには、約22日 ×（日を開く → この割当で確定 → 確定する → 戻る）＝約90回の操作が要る。ホームの「確定していない日 N日」も月の画面へ移るだけ
- 初期データは案を持たない（`aiPlans: {}`）。初めて開くと月は今日以降が赤い「案なし」、空き状況は「？」、週は空。AI の案は、日を開く（自動で作る）か「まとめて作る」（1〜2分）まで見えない
- 案内ツアー（5枚）は場所の説明だけで、閉じたあとに何を押せばよいかが無い

調査（2026-10-19）：8人・約17件の日を `solve` で解くと、既定の反復（`defaultIterations`。約220万回）で 1日 約0.6〜1.1秒（開発機の node）。10万回なら 約30〜40ms で、点数は既定の反復と1点以内（7日とも入らない訪問 0件）。日の状態（入らない・必須の違反・休みの人に残る訪問）は `useDayStatuses` の1か所で数え、月・ホーム・帯で同じ。
制約：データを書くのは store の `update(fn)` だけ。契約（`AiPlan`・`AiRun`）に項目を足さない。seed・solver は乱数・`Date.now` を使わない。外部送信を増やさない。「確定」の意味（ADR-0004・0009）は変えない。

## 決定
1. **問題の無い日をまとめて確定**（月の右の欄の「確定していない日」）：今日以降の一度も確定していない日（案あり・未確定）のうち、必須の違反が0で、月の要対応（入らない訪問・休みの人に残る訪問・条件が変わった・拘束超・欠勤）に出ない日を、独自の確認のあと1回の `update` で確定する。日の状態は `useDayStatuses`、要対応は `attentionList` のものを使い、数え直さない。書き方は日の画面の「この割当で確定」と同じ純粋関数 `lib/confirmDay` の `confirmDay`（日の画面もこれを呼ぶ）。確認には日付と、残す日（問題のある日は日付も、未確定の変更ありの日・案の無い日は日数）を出す。0日なら押せず理由を見せる
   - 要対応に出ている日は、見るだけの種類（拘束超・欠勤・条件が変わった）でも黙って確定しない
   - 未確定の変更ありの日（前に確定した割当と今の案が違う）は対象にしない。確定した割当をまとめて置き換えず、日の画面で差を見て確定し直す
   - 対象は右の欄の一覧と同じ今日以降。日の画面は今日より前でも確定できるが、まとめては見えている一覧の範囲だけにする
2. **次の確定していない日へ**：日の画面で確定済みのとき、見出しの印の横に「次の確定していない日へ（M/D）」（その日より後・今日以降、その日の月と翌月で、`useDayStatuses` の数え方の確定していない日の最初）。知らせ（トースト）は文だけの部品なので、状態の横に置く
3. **初期データに案を同梱**：起動したとき（データが無い・読めない・初期状態に戻す）に `seed/plans` の `createInitialData(today)` が、今日から7日分を点数の基準のプリセット（「標準」）で同期に解き、月の「まとめて作る」と同じ `applyDayRun`（記録1件・`inputKey`・今の案はその記録）で書く。反復は `min(defaultIterations, 100000)`、種はデータの `seed`、`createdAt` はその日の日本時間 0:00。同じ日付なら同じデータ。確定はしない。`createDemoData` は今のまま（案なし。単体テストの土台）
4. **ツアーの最後の一手**：最後の枚を「AI案 → 手直し（固定）→ 確定」の3段の説明にし、主ボタン「今日の予定を開く」（閉じて今日の日の画面）と「閉じる」で終える（最後の枚に「とばす」は出さない）。6枚

## 検討した案
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| 初期の案A：起動で同期に解く（反復を10万回に減らす） | 決定的で単体テストで確かめられる。Worker・待つ表示が要らず、初めの描画から中身がある | 起動が 約0.3秒（遅い端末で1秒ほど）延びる。既定の反復の案より少し劣ることがある（1点以内） | 採用 |
| 初期の案A'：起動で同期に解く（既定の反復） | 日の画面で作る案と同じ質 | 7日で 約5〜7秒、画面が固まる | 不採用 |
| 初期の案B：起動のあと Worker で7日分を作り、進み具合の帯を出す | 画面は固まらない。既定の反復で作れる | 最初の数十秒は「案なし」のまま。まとめて作る・日の画面の自動作成と Worker（1つ）を取り合い、確かめる流れが増える | 不採用 |
| 初期の案C：作った案を JSON で `src/seed/` に同梱 | 起動は速い | 日付が今日から決まるので、訪問の ID・日付が合わない（日付ごとに作り直しが要る）。条件・プリセットを変えるたびに作り直す | 不採用 |
| まとめて確定A：今の案があり、入らない・必須の違反・休みの人に残る訪問が0の日 | 手数が最も減る | 条件が変わった日（重みを変えた）・拘束超・欠勤の日も黙って確定する | 不採用 |
| まとめて確定B：要対応に1つでも出る日（条件が変わった・拘束超・欠勤も）を外す | 要対応に出ている日を黙って確定しない（月の要対応と同じ判定） | 振り直し済みの欠勤の日・拘束の注意だけの日は日の画面で確定する | 採用 |
| まとめて確定（未確定の変更あり）：含めて置き換える | 日の画面の「この割当で確定」と同じ範囲 | 前に確定した割当（〈スタッフ〉に伝えた予定）を差を見ずに置き換える | 不採用 |
| まとめて確定C：案のある日をすべて確定 | 単純 | 入らない訪問がある案を確定してしまう | 不採用 |
| まとめて確定D：今日より前の日も含める | 日の画面と同じ範囲 | 「確定していない日」の一覧（今日以降）と数が食い違う | 不採用 |
| 次の日へA：確定済みの印の横にボタン | 状態で決まり、読み直しても出る | 見出しが少し混む | 採用 |
| 次の日へB：確定の知らせ（トースト）に操作を付ける | 確定の直後だけ | トーストは2.5秒で消える文だけの部品で、キーボードで届かない | 不採用 |

## 結果・トレードオフ・見直す条件
- 得るもの：一月の確定が約90回の操作から確認を含む2回に。初めて開いた人に、月・週・空き状況・ホームで AI の案（7日分）がすぐ見える。ツアーのあとに1手で日の画面へ移れる。「確定」の書き方が1か所（`confirmDay`）になる
- 失うもの：
  - 初めて開くとき・初期状態に戻すときに 約0.3秒待つ（遅い端末で1秒ほど）。初期の案は既定の反復で作り直すと少し変わることがある
  - まとめて確定は1日ずつ案を見ずに確定する（一度も確定していない問題の無い日に限り、確認に日付を出して補う）。要対応に出る日・未確定の変更ありの日は日の画面で1日ずつ確定する
  - 初期データを前提にした e2e（案なしから始める確かめ）は、先に案を消してから始める
- 見直す条件：起動の待ちが気になる声が出たら案B（Worker で作る）へ。まとめて確定で「拘束の注意・欠勤の日もまとめて確定したい」という声が多ければ、見るだけの要対応を対象に戻すか選べるようにする
- 影響：PRD D1 の初期データに AI案（D225）、D192 のツアーを6枚に。design.md §4 の seed・store、design/pages-month・pages-plan・pages-common
