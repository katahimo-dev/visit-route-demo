# ADR-0007：点数を100点満点（高いほど良い）で見せる

- 日付：2026-10-13
- 状態：採用（点数の式は末尾の「案A への変更（2026-10-13）」で置き換えた。下の「決定」の式と1.6倍は経緯として残す）

## 背景
画面の合計点は、solver が最小にする費用（移動1分＝1点＋条件の点。低いほど良い）をそのまま出していた。利用者から「543点が良いのか悪いのかわからない」「低いほど良いのが直感に反する」という声が出た。費用は日・訪問の数・条件の重みで大きさが変わり、目安がない。

決めること：費用を、日をまたいでも読める「100点満点・高いほど良い」の点数にどう直すか。探し方（solver が最小にする費用）は変えない。

## 選択肢
1. 案A：理想と素朴な案のあいだ。100点＝理論上の下限（届かない理想）、0点＝その日のデータから決定的に作る素朴な案。そのあいだを費用の一次変換で直す
2. 案B：減点方式。100点から、移動・条件の違反などを決まった割合で引く
3. 案C：その日の記録のうち最良の案を100点にする

## 決定
案A（利用者が選んだ。2026-10-13）。

- 下限 LB＝割当の下限＋移動の下限（待ち0・負担の均等0）。どの案（必須を守る案）の費用も LB 以上
  - 割当：各訪問を、可否を満たす担当のうち割当費用（assignCost）が最小の人にした合計
  - 移動：max(Σ 各訪問に来る移動の最小, Σ 各訪問から出る移動の最小)。来る元＝担当できる人の自宅か前に置けうる訪問、出る先＝担当できる人の自宅か後に置けうる訪問（帰りの移動も費用に入るので、出る側も下限になる）
  - 1件ごとの割当＋移動の下限が落とした訪問の点を超えるなら、落とした訪問の点にする。担当の候補がいない訪問は落とした訪問の点（どの案でも避けられない）
  - 当初は移動の下限を0にしていたが、届かなすぎて良い案でも40点前後に見えたため、移動の下限を入れた（2026-10-13）
- 素朴な案 N＝訪問を開始（earliest）の早い順に、可否・件数の上限・時間の約束・稼働時間帯を満たす担当のうち、直前の場所からの移動が最短の人の最後に足した案を evaluate.score で採点した費用。入れられない訪問は入らない
- 点数＝round(100 × (N − 費用) / (N − LB))、0〜100 に収める。N ≤ LB なら 100
- 内訳＝費用の成分（移動（下限との差）・待ち・担当の条件（下限との差）・負担の均等・入らない訪問）ごとの超過 × 100/(N − LB) を「−x点」で示す

## 理由とトレードオフ
- 得るもの：
  - 費用の単調な変換なので、案の順位は費用と必ず一致する（solver・比較の結論は変わらない）
  - 0点の意味（機械的に割り当てた案と同じ）と100点の意味（どの案も越えられない下限）が説明できる
  - 内訳で「どこで点を失ったか」が成分ごとに見える
- 失うもの：
  - 下限は現実には届かないので、良い案でも 50点前後に見える（seed の 2026-10-13 で AI案は 45〜49点）。移動の下限は「いちばん近い場所から来る」緩めた値で、実際の移動の 3分の1ほど
  - 素朴な案が訪問を落とすと N に落とした訪問の点（1件 10000）が入り、点の幅が大きくなって差が縮む
  - 物差しは条件（重み）で変わる。条件を変えると同じ案でも点が変わる（比較の画面は A・B ともいまの条件で付け直すので比べられる）
  - 丸めるので、費用がわずかに違う案が同じ点になることがある

## 影響
- evaluate に `normalize(problem): ScoreScale`・`toHundred(cost, scale)`・`hundredBreakdown(score, scale, problem)`・`naivePlan(problem)` を足す。型 `ScoreScale`・`HundredPart` は `src/contracts/problem.ts`
- matching・solver の費用の定義・`SolveResult.score`・`PlanScore.total` は変えない（内部の値のまま）
- 画面（AI案・比較・予定）の合計点を100点満点にし、内部の費用は説明（Hint）に「費用 543（内部の値）」として残す
- 見直す条件：「点が低く見える」という声が強ければ、100点を下限ではなく達成しやすい目標（例：記録の最良）に寄せる案C を検討する

## 追記（2026-10-13）：点数を1.6倍にする
- 背景：移動の下限を入れたあとも、良い案でも 50点前後に見え、「良い案なのに半分しか取れていないように見える」という声が出た（1.6倍で 50点→80点）
- 決定（利用者が決めた。2026-10-13）：上の点数（下限＝100・素朴な案＝0 の一次変換）に **1.6 を掛けて**出す。点数＝round(160 × (N − 費用) / (N − LB))。下は 0 で止め、上は 100 を超えてよい（理論上の最大 160。N ≤ LB なら 160）。表示は「72点」（「/100」は付けない）。内訳（−x点）も 1.6 倍してそろえ、合計はおおむね 160−点数
- 理由：一次変換に定数を掛けるだけなので、順位は費用と一致したまま（solver・比較の結論は変わらない）。0点の意味は変わらない
- トレードオフ：「100点満点」とは言えなくなる（100点を超えることがある）。説明（Hint）に「理想と素朴な案のあいだを1.6倍した点。100点を超えることもある」と書く
- 影響：evaluate の `toHundred`・`hundredBreakdown` が 1.6 倍の値を返す（関数名は互換のため変えない。倍率は `SCORE_MULTIPLIER`）。画面の「100点満点」の文言をやめる

## 追記（2026-10-13）：素朴な案の作り方と、AI案が素朴な案より悪くならないこと（レビューの指摘）
- 問題1：素朴な案を「最後に足す」で作ると、日曜（2〜3人・すべて時刻ちょうど）に 16時の訪問を落とし（先に 15:30 の訪問が唯一の候補の人に入る）、N に落とした訪問の点（10000）が入って物差しが潰れ、どの案も 150点台になっていた（10-18・10-25）
- 問題2：焼きなましの貪欲な初期解が素朴な案より悪い日があり、AI案が0点になっていた（10-17・10-25 など）
- 決定：
  - 素朴な案は、担当できる人の少ない訪問から（同じなら開始の早い順に）、増える移動が最も少ない担当の、その順番の中で最も移動の増えない位置（strict で入る位置）に挟む。条件の点は見ない。それでも入らない訪問だけ落とす
  - solver は、貪欲な初期解と素朴な案の費用の低い方から始める（決定的なまま）。AI案の費用 ≤ 素朴な案なので、AI案の点は 0 以上
  - 必須の違反がある案（手作業案など）は、下限・素朴な案の前提（必須を守る）から外れるので、点に「参考」の印を付ける
- 実測（seed を 2026-10-12 に作り、14日・初期のプリセット3つ。各プリセットの条件の物差しで。既定の反復回数）：
  - 素朴な案が訪問を落とす日：0日（直す前は日曜の2日）
  - 平日（10日）：AI案は 39〜81点（標準 60〜72点、移動を短く 39〜66点、人の組み合わせ重視 63〜81点）
  - 土日（4日。2〜3人・8件・すべて時刻ちょうど）：0〜41点。10-24・10-25 の「移動を短く」は、種を5つ・反復5倍にしても素朴な案と同じ費用で 0点（組み方の余地がほとんどなく、素朴な案が最良と見られる）。0点は「機械的な案と同じ」の意味のまま残し、カードの王冠は付けない
  - いまの条件（標準）の物差しでのカードの点：0〜72点。2026-10-13 は 標準 60・移動を短く 49・人の組み合わせ重視 57
- トレードオフ：素朴な案が賢くなったぶん、点は全体に少し低めに出る（以前の 10-13 標準 74点 → 60点）。下限（160点）は待ち0などで届かないので、良い案でも 60〜80点前後

## 案A への変更（2026-10-13）：1件あたり、理想より余計にかかった分だけ減点する
- 経緯：
  1. 当初は「下限＝100点・素朴な案＝0点」の一次変換。良い案でも 50点前後に見えた
  2. 1.6倍にして 80点前後に見えるようにした（上限 160。100点を超えることがある）
  3. 素朴な案を賢くし、solver の初期解に入れた（上の追記）。すると土日（2〜3人・8件・すべて時刻ちょうど）のように素朴な案が最適に近い日は、N − LB が小さくなって物差しの幅が潰れ、AI案が 0〜18点になっていた。AI案の質を「1件あたり、理想より余計にかかった費用」で見ると平日 29〜32分・土日 36〜42分で大差ないのに、点では大きく違って見えた
- 決定（利用者が決めた。2026-10-13）：
  - 点数＝round(100 −（費用 − LB）÷ 訪問の件数)、0〜100 に収める。100点＝理想（下限 LB）。「1件あたり、理想より余計にかかった費用（分に換算）だけ減点」（1件あたり10分余計なら90点）。表示は「70点」
  - 訪問の件数＝その日の `Problem` の訪問の数（計算に入れた訪問。`ScoreScale.visits`）。0件なら100点
  - 下限 LB の定義（割当の最小＋移動の下限、落とした訪問の点の上限つき）は変えない
  - 倍率 1.6・上限 160 はやめる（`SCORE_MULTIPLIER` を消し、`SCORE_MAX`＝100）
  - 素朴な案は solver の初期解の候補（AI案の費用 ≤ 素朴な案）として残し、点数の基準には使わない。`ScoreScale` から `naive`・`naiveRoutes` を外す（`naivePlan(problem)` は残す。テストは `score(problem, naivePlan(problem))` で素朴な案の費用を出す）
  - 内訳：成分ごとの超過 ÷ 訪問の件数 を「−x点」で示す（合計＝100−点数。0 未満の成分は画面に出さない）
  - 必須の違反がある案の「参考」の印はそのまま
- 理由：
  - 費用の単調な変換なので、同じ日なら順位は費用と一致したまま（solver・比較の結論は変わらない）
  - 素朴な案に依らないので、素朴な案が最適に近い日でも幅が潰れない。「1件あたり何分余計か」で、日をまたいでも同じ意味で読める
- トレードオフ：
  - 下限は現実には届かないので、良い案でも 60〜80点前後（満点は出ない）
  - 1件あたりの超過は条件の重みで変わる（重みが大きいプリセットは点が低く出やすい）。プリセットどうしの点は「いまの条件」の同じ物差しで比べる
  - 素朴な案が訪問を落とす・AI案が訪問を落とすと、1件で 10000 ÷ 件数の減点になり 0点に張り付く
- 実測（seed を 2026-10-12 に作り、14日・初期のプリセット3つ。各プリセットの条件の物差しで。既定の反復回数）：
  - 標準：平日 67〜71点・土日 58〜64点
  - 移動を短く：平日 76〜79点・土日 67〜71点
  - 人の組み合わせ重視：平日 60〜69点・土日 58〜63点
  - 2026-10-13：標準 68点（素朴な案は 50点）・移動を短く 76点・人の組み合わせ重視 65点
- 影響：`toHundred`・`hundredBreakdown` の式、`ScoreScale`（`visits` を足し `naive`・`naiveRoutes` を外す）、画面の説明文（「理想を100点として、1件あたり理想より余計にかかった分（分換算）だけ減点」）。「100点を超えることもある」「素朴な案を0点」の文言を消す
