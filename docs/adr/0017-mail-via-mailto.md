# ADR-0017：メール連携は mailto: でメールアプリを開くだけ（アプリからは送らない）

- 状態：採用（2026-10-17）
- 関連：PRD D91〜D96、ADR-0016（外部送信の決まり）、ADR-0018（道順リンクの追加）

## 背景
日の予定・週の予定・欠勤の振り直しの連絡・空き枠の案内文（D67）は、画面で見るか、文をコピーして別のメールアプリ・LINE に貼っていた。宛先を選び、件名を書き、本文を貼る手間を減らしたい。
PRD §7・AGENTS.md は外部送信を地図タイルと押したときの郵便番号・住所の検索だけにしており、メールの送り方によってはぶつかる。
決めること：どう送るか、どの項目・場面か、本文の形と長さ、鍵の情報の扱い、宛先が無い・複数のとき。

## 決定
`mailto:` のリンクで OS の標準メールアプリを宛先・件名・本文入りで開くだけにする。送信は人がメールアプリで押す。

- 外部送信の決まりとの関係：mailto はブラウザが OS のメールアプリへ渡すだけで通信は起きない。送るか・宛先・本文の直しは人がメールアプリで決める。PRD §7・AGENTS.md の外部送信の決まりは変えない
- 項目：〈スタッフ〉の `email`、〈利用者さん〉の紹介元の `referrer.email`（任意・既定 ''。版は1のまま）。形の検査は緩く（空か、空白・@・区切り「,;<>"」と URL を壊す「?&=%#/」を含まない文字 ＠ 同じ。254字まで）。全角・前後の空白・「mailto:」は保存・読み込み時に直す（`normalizeEmail`）。Excel は〈スタッフ〉に「メールアドレス」、〈利用者さん〉に「紹介元のメールアドレス」（任意の列。形が合わない値は場所付きで止める。リンクのセルは表示を読み、無ければ「mailto:」以降）
- 場面（どれも主ボタンにしない）：
  1. 日の予定（担当ごと）：担当は確定した割当があればそれ、無ければ今の案。件名「10/18（日）の訪問予定」。本文は順番・時刻・〈利用者さん〉様・住所・入り方・駐車場・注意・事業所名。欠勤・希望休の人は「欠勤」「希望休」と出す
  2. 週の予定（担当ごと）：曜日ごとの訪問（時刻・〈利用者さん〉様）。確定した割当、無ければ今の案（「案。まだ確定していません」）。住所・決まりごと・鍵は入れない。最終勤務日が週の初めより前の人は出さない
  3. 欠勤の振り直しの連絡：連絡の一覧の〈スタッフ〉あて連絡文の「コピー」の横に「メール」（変わった訪問と新しい時刻）
  4. 空き枠の案内文（D67）：「紹介元へメール（BCC N件）」。宛先は紹介元のメールを重複なく（大文字・小文字は同じ）集め、チェックで外せる（画面の中だけ）。To は空で BCC に並べ、宛先どうしにアドレスを見せない。目安を超えるときは宛先を前から分けて複数ボタン（`buildBccMails`）にし、「宛先をコピー」も並べる
- 本文は文字だけ（HTML にしない）。改行は CRLF。件名・本文・宛先は `encodeURIComponent`
- 長さの目安（`mailLimitFor` が `userAgentData.platform` と `userAgent` から決める）：Windows・判定できない端末は 2000字（Windows は 2048字付近で切る・開かないことが知られ、余裕を見た）、iOS・Android・macOS は 8000字（標準メールアプリはもっと長い URL を受けるが、際限なく長いと遅くなるので止める）。判定を外したら安全側の 2000 に倒す
- 超えたとき：日の予定は要点に2段（要点1＝順番・時刻・利用者さん・住所、要点2＝順番・時刻・利用者さんだけ）、週は曜日ごとの時刻と件数に絞る。それでも超えれば本文を入れず「長いため、…」と「本文をコピー」を並べる。欠勤の連絡・空き枠の案内は要点を持たず、超えれば本文なし＋コピー。本文なしでも超える（宛先・件名が長すぎる）ときは `tooLong` で aria-disabled＋理由
- 鍵の情報：既定では入れない。日の予定の欄の「鍵の情報も入れる」を選んだときだけ入れる（既定オフ。画面の状態のみで保存しない）。入れないときは「鍵の情報はメールに入れていません」と書く。週・連絡・案内には入れない
- 宛先が無いとき：aria-disabled＋理由「メールアドレスが未登録です」（紹介元が1つも無い・全部外したときは別の文）。日・週・連絡は To に1人、案内は BCC
- 日の予定のメールには ADR-0018 の道順リンクが入り、長さの目安を超える段階の順は ADR-0018 に従う
- 組み立ては純粋関数：`lib/mailto.ts`・`lib/mail.ts`。画面は `<a href="mailto:…">`。画面の細部は design.md

## 検討した案
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| 送り方A：mailto でメールアプリを開く | 手書き不要で送る前に見直せる（誤送信を止められる）。外部送信・キー・費用が要らず静的サイトのまま | メールアプリ未設定だと何も起きない。送ったかは分からない | 採用 |
| 送り方B：送信サービスの API を呼ぶ | 自動で送れる | 個人の予定・住所を外へ送り PRD §7 を大きく変える。キーを公開リポジトリに置けない・費用・送信の記録が要る | 不採用 |
| 送り方C：コピーだけ（従来） | 変更なし | 宛先・件名を毎回書く手間が残る | 不採用（長いときの逃げ道として残す） |
| 長さA：目安を超えたら要点→本文なし＋コピー | 切れずに済む | 要点になる・貼る手間が残る | 採用 |
| 長さB：長さを見ずにすべて入れる | 単純 | OS・メールアプリで途中が切れる | 不採用 |
| 鍵A：既定オフで選んだときだけ | 転送・誤送信のリスクを毎回判断できる | 毎回選ぶ手間 | 採用 |
| 鍵B：いつも入れる／C：入れない | 手間なし／最も安全 | 漏れるおそれ／鍵を伝えられない | 不採用 |

## 結果・トレードオフ・見直す条件
- 得るもの：宛先・件名・本文を書かずに済み、メールアプリで見直せる。外部送信の決まりを変えず、鍵の情報は既定で入らない
- 失うもの：
  - 端末にメールアプリが設定されていないと押しても何も起きない（注記に「この端末のメールアプリが開きます」。コピーは使える）
  - Windows の目安 2000字は日本語で本文約200字（1字が9字になる）で、決まりごとの多い日はほぼ要点になる。実機での切れ方は未測定（Linux のヘッドレス Chromium では日の予定 910〜1696字・週 1940字が全文で収まった）
  - 送ったかどうかは記録しない（PRD §4 の「通知・記録はやらない」のまま）。宛先の形は緩くしか見ない
- 見直す条件：実機（Windows の Outlook・新しい Outlook・Gmail 既定の Chrome、iPhone のメール、Android の Gmail、macOS のメール）で切れ方を測り、`MAILTO_LIMIT_SAFE`・`MAILTO_LIMIT_LONG` と `mailLimitFor` を見直す。「切れる」「要点で足りない」の声も同じ。送ったかの記録・自動送信が要るなら別の ADR でサーバー側の送信を考える
- 影響：PRD に「メールの送信・送った記録はやらない（メールアプリを開くだけ）」と、mailto は外部送信に当たらない旨を追記
