# ADR-0017：メール連携は mailto: でメールアプリを開くだけ（アプリからは送らない）

- 日付：2026-10-17
- 状態：採用（利用者が推奨どおりに決定（2026-10-17）。細部は推奨どおりに決め、この ADR に記録する）

## 背景
日の予定・週の予定・欠勤の振り直しの連絡・空き枠の案内文（D67）は、いまは画面で見るか、文をコピーして別のメールアプリ・LINE に貼り付けている（連絡の一覧は「コピーするだけで、送信はしません」。PRD §4「案内文の送信（コピーだけ）」）。
宛先を選び、件名を書き、本文を貼る手間を減らしたい（第8弾の要望）。

PRD §7・AGENTS.md は「利用者が入れたデータは端末の外に送らない（外部送信は地図タイルと、押したときの郵便番号・住所の検索だけ。ADR-0016）」としている。メールを送る方法によっては、この決まりとぶつかる。

決めること：(1) どう送るか、(2) どの項目・どの場面か、(3) 本文の形と長さ、(4) 鍵の情報の扱い、(5) 宛先が無いとき・複数のとき。

## 選択肢
1. 送り方
   - A：**`mailto:` のリンクで、OS の標準のメールアプリを宛先・件名・本文の入った状態で開く。送信は人がメールアプリで押す**
   - B：メールの送信サービス（API）をアプリから呼んで送る
   - C：今までどおりコピーだけ
2. 長い本文
   - A：**mailto の URL（エンコード後）の長さが目安（1800字）を超えるなら要点に絞り、それでも超えるなら本文を入れずに「本文をコピー」を並べて知らせる**
   - B：長さを見ずにすべて入れる（メールアプリ・OS によっては途中で切れる）
3. 鍵の情報
   - A：**既定では入れない。「鍵の情報も入れる」を選んだときだけ（既定オフ。画面の中だけの状態で保存しない）**
   - B：いつも入れる
   - C：入れない

## 決定
1-A、2-A、3-A（送り方は利用者が決定。細部は推奨どおり）。

- 外部送信の決まりとの関係：mailto はブラウザが OS のメールアプリへ渡すだけで、アプリから外部のサービスへは何も送らない（通信は起きない）。メールを送るかどうか・宛先・本文の直しは、人がメールアプリで決める。だから PRD §7・AGENTS.md の外部送信の決まりは変えない（地図タイルと郵便番号・住所の検索だけのまま）
- 項目：〈スタッフ〉の `email`、〈利用者さん〉の紹介元（D73）の `referrer.email`。どちらも任意・既定 ''（zod の既定値。`DATA_VERSION` は1のまま）。形の検査は緩く（空か、空白・@・「,;<>"」を含まない文字 ＠ 同じ。254字まで）、入力の全角・前後の空白・「mailto:」は保存・読み込みのときに直す（`lib/mailto` の `normalizeEmail`）。Excel は〈スタッフ〉に「メールアドレス」（「最終勤務日」の次）、〈利用者さん〉に「紹介元のメールアドレス」（「紹介元のメモ」の次）。どちらも任意の列で、無い古いブックは空。形が合わない値はシート名・行付きで止める
- 場面（どれも主ボタンにしない）：
  1. 日の予定（担当ごと）：日の画面の「メールで送る」→ 欄に担当ごとの「メールを作る」。担当は確定した割当があればそれ、無ければ今の案（`printDay` と同じ決め方。欄と本文にどちらかを書く）。件名「10/18（日）の訪問予定」。本文は 順番・時刻・〈利用者さん〉様・住所・入り方・駐車場・注意（D66）、事業所名
  2. 週の予定（担当ごと）：週の〈スタッフ〉×曜日の表の「週の予定をメールで送る」→ 欄に担当ごと。件名「10/19〜10/25 の予定」。本文は曜日ごとの訪問（時刻・〈利用者さん〉様）。日ごとに確定した割当、無ければ今の案（「案。まだ確定していません」と書く）。訪問の無い日は 希望休・欠勤・休み・予定はまだ決まっていません・訪問なし を書く。住所・決まりごと・鍵は入れない
  3. 欠勤の振り直しの連絡：連絡の一覧の〈スタッフ〉あての連絡文の「コピー」の横に「メール」。件名「10/18（日）の予定の変更」。本文は連絡文（変わった訪問と新しい時刻。`staffMessage`）＋事業所名
  4. 空き枠の案内文（D67）：案内文の「コピー」の下に「紹介元へメール（BCC N件）」。宛先は紹介元のメールを重複なく（大文字・小文字は同じとみなす）集め、チェックで外せる（画面の中だけ）。To は空で BCC に並べる（宛先どうしにアドレスを見せない）。件名「空き枠のご案内（事業所名）」。本文は案内文
- 本文は文字だけ（HTML にしない）。改行は CRLF（%0D%0A）。件名・本文・宛先は `encodeURIComponent`（宛先の @ は読めるまま）
- 長さ：URL の長さ（エンコード後）の目安 `MAILTO_LIMIT = 1800`。超えるなら要点（日：順番・時刻・〈利用者さん〉・住所（鍵を選んだときは鍵も）、週：曜日ごとの時刻と件数）に、それでも超えるなら本文を入れない。要点・本文なしのときは、ボタンの横に「長いため、…」と「本文をコピー」（すべての本文）を出す。欠勤の連絡・空き枠の案内は要点を持たず、超えれば本文なし＋コピー
- 鍵の情報：日の予定の欄の「鍵の情報も入れる」（既定オフ。React の状態だけで保存しない。欄を閉じると戻る）。入れないときは本文に「鍵の情報はメールに入れていません」。週・連絡・案内には入れない
- 宛先が無いとき：ボタンは aria-disabled＋理由「メールアドレスが未登録です」（title・読み上げ・小さな文。押すとトーストでも出す）。紹介元のメールが1つも無いときは「紹介元のメールアドレスが未登録です（…の画面の「紹介元のメールアドレス」で入れられます）」、全部外したときは「宛先を1つ以上選んでください」
- 宛先の数：日・週・連絡は To に1人。案内は BCC に並べる
- 組み立ては純粋関数：`lib/mailto.ts`（`normalizeEmail`・`mailtoHref`・`buildMail`・`uniqueRecipients`・`MAILTO_LIMIT`）と `lib/mail.ts`（件名・本文。`dayByStaff`・`dayMailText`・`weekByStaff`・`weekMailText`・`contactMailText`・`vacancySubject`・`referrerRecipients`・`mailTo`）。画面は `<a href="mailto:…">` で開く。呼び方は `org.terms`、事業所名は `org.name`

## 理由とトレードオフ
- 得るもの：
  - 宛先・件名・本文を手で書かずに済み、送る前にメールアプリで見直せる（誤送信を止められる）
  - アプリからは何も送らないので、外部送信の決まり・キー・費用・送信サービスの規約が要らない。静的サイトのまま
  - 鍵の情報は既定で入らず、入れるかを毎回その場で選ぶ（メールは転送・誤送信で人の目に触れうる）
- 失うもの：
  - 端末にメールアプリが設定されていないと、押しても何も起きない（ブラウザ・OS の設定。注記に「この端末のメールアプリが開きます」と書く。コピーは今までどおり使える）
  - URL の長さの限りで、長い本文は要点になるか、コピーして貼る手間が残る。目安の 1800字は日本語で本文 180字ほど（1字が9字になる）で、決まりごとの多い日はほぼ要点になる
  - 送ったかどうかは分からない（記録しない。PRD §4 の「通知・記録はやらない」のまま）
  - 宛先の形は緩くしか見ないので、綴りの誤りはメールアプリで気づくことになる
- B（送信サービス）を採らなかった理由：外部へ個人の予定・住所を送ることになり、PRD §7 を大きく変える。キーをビルドに入れられない（公開リポジトリ）・費用・送信の記録が要る
- C（コピーだけ）を採らなかった理由：宛先・件名を毎回書く手間が残る。コピーは長いときの逃げ道として残す

## 影響
- PRD：D91〜D96 を追加。§4 に「メールの送信・送った記録はやらない（メールアプリを開くだけ）」。§7 に mailto は外部送信に当たらない旨
- design.md：§2、L3（`lib/mail`・`lib/mailto`）、store（既定値）、excel（列）、pages（第8弾）、§5「メール連携（mailto）」、§7 代替案、§8
- データ：`DATA_VERSION` は1のまま（`email`・`referrer.email` は zod の既定値 ''）
- 見直す条件：利用者から「切れる」「要点で足りない」の声が出たら `MAILTO_LIMIT` を見直す（1か所の定数）。送ったかの記録・自動の送信が要るなら、別の ADR でサーバー側の送信を考える
