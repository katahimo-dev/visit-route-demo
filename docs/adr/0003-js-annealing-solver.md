# ADR-0003：最適化はブラウザの Web Worker 上の焼きなまし（TypeScript）で解く

- 日付：2026-10-11
- 状態：採用

## 背景
静的サイトなので Python（OR-Tools）は動かない。割当費用（相性・希望・継続）と均等の費用を目的関数に入れたい。8人・20件を数秒、30人・150件を30秒以内で解きたい。同じ入力から同じ案を出したい（再現性）。

## 選択肢
1. 案A：OR-Tools を WebAssembly にする
2. 案B：Pyodide で Python の optimizer を動かす
3. 案C：TypeScript で焼きなまし（ClassClassify の `anneal.ts` の構成：貪欲な初期解・差分評価・指数冷却・最後に貪欲な仕上げ）

## 決定
案C。近傍は「別の担当へ移す（実行可能な位置へ挿入）」「2つの訪問の担当を入れ替える」「同じ担当の中で順番を入れ替える」「落とした訪問を入れる」。
時間の約束・稼働時間帯・可否はハード（破る手は採らない）。乱数は seed 付き（mulberry32）、止めるのは反復回数（時刻で止めない）。
複数の seed を並列の Worker で回して最良を採るのは、結果の決め方（点数→seed の小さい順）を固定したうえで改修時に足す。

## 理由とトレードオフ
- 得るもの：依存なし・ビルドが軽い・任意の費用関数を入れられる・ClassClassify の実装と考え方を流用できる
- 失うもの：最適性の保証、OR-Tools との数値の一致。PoC本体の AI案とは結果が違う
- 反復回数で止めるため、端末が遅いと時間がかかる → 30秒で `stop` して最良案を採る（そのときは「途中の案」と表示）

## 影響
- 「全条件の重み0・移動だけ」で PoC本体の seed の手作業案より総移動が短いことをテストで確かめる
- 見直す条件：30人・150件で 30秒を超える、または移動だけの案が OR-Tools より 10% 以上悪いとき

## 追記（2026-10-12）：OR-Tools との比較

詳細は [docs/optimization-benchmark.md](../optimization-benchmark.md)。
- デモデータ（8人・約17件／日、10日分）：移動だけの問題で OR-Tools と総移動時間が完全に一致
- 大規模（15〜50人・60〜250件）：既定の反復回数（約2秒）では OR-Tools 60秒より 2〜18% 悪く、見直し条件（10%）を超えるケースがある。5倍（約7〜11秒）では −1.7〜+5.6%
- 対応：既定の反復回数を規模に応じて増やす。5倍でも10%以上悪くなる規模になったら ALNS に広げる
