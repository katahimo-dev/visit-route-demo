# ADR-0011：当日の急な欠勤を別の記録で持ち、他の人の予定を変えずに空き時間へ振り直す

- 日付：2026-10-13
- 状態：承認（1回目＝案A の範囲。細部は 2026-10-13 に利用者が推奨どおりに決定。design.md §8 の「決めたこと」）

## 背景
利用者から「当日のスタッフの急な欠勤で、**他のスタッフのそれまでの予定を極力変えずに**、欠勤の人の訪問を振り直したい」と要望が出た（2026-10-13）。
終日の欠勤だけでなく、途中の欠勤（午前だけ病院の付き添い＝9:00〜12:00 だけ不在、〇時から早退、〇時まで遅刻）も扱う。

いまできるのは、稼働時間の画面でその日の時間帯を上書きし、「AI案を作る」で全部組み直すか、ドラッグで1件ずつ手で移すことだけ。

- 全部組み直すと、欠勤と関係のない人の担当・順番・時刻まで変わり、利用者さん・スタッフへの連絡が増える（当日は連絡そのものが負担）
- 稼働時間を上書きすると、元の稼働時間が消え（取り消せない）、「なぜ時間が減ったか」（欠勤・メモ）が残らない
- ドラッグでは、どの訪問を誰に移せば入るかを人が探すことになる

決めること：(1) 欠勤の持ち方、(2) 振り直し方、(3) 振り直しの置き場所、(4) 振り直した結果の扱い、(5) 1回目と2回目の範囲。

## 選択肢
1. 欠勤の持ち方
   - A：稼働時間の上書き（`availability`）に書く（欠勤の時間を除いた時間帯で上書き）
   - B：**別の記録**（`absences: { id, staffId, date, from, to, note }[]`。終日は from・to とも null）として持ち、稼働時間帯の計算で差し引く
2. 振り直し方
   - A：**挿入だけ**（案A「空き時間に入れるだけ」）：他の人の担当・順番・開始時刻を変えず、振り直す訪問を、入れられる人の少ない順（同じなら regret の大きい順）に、費用の増えが最も少ない strict の位置へ1件ずつ入れる
   - B：変更の減点つき焼きなまし（案B「少し動かしてよい」）：solver の費用に、元の案から担当を変えた訪問への減点を足して解く
   - C：全部組み直し（いまの「AI案を作る」を欠勤を差し引いた時間帯で）
3. 置き場所
   - A：matching に足す（`bestInsertion` の隣）
   - B：solver に足す
   - C：**新しいコンポーネント reassign**（`src/reassign/`）
4. 結果の扱い
   - A：**今の案（AiPlan）にして全部固定**、記録（AiRun）にも振り直しの情報を付けて残す
   - B：今の案とは別の「欠勤の案」を持つ

## 決定
1-B、2-A（1回目）＋2-B（2回目）、3-C、4-A。1-B・2-A・4-A は利用者の方向づけ（2026-10-13）、細部（データの形・規則・置き場所）はこの ADR と design.md に書いた。

- データ：`DemoData.absences`（zod の既定値で `[]`。DATA_VERSION は1のまま、`aiRuns`・`presets` を足したときと同じ）。時刻は30分単位、`from` が null＝始業から、`to` が null＝終業まで、両方 null＝終日。1人1日1件（store の repair は稼働時間の上書きと同じく最後の1件）。Excel に「欠勤」シート（無い古いブックは欠勤なし）
- 差し引き：domain の `withoutAbsences`（デモ独自。`domain/availability.ts` に置き「働ける時間帯を決めるのはこのファイルだけ」を保つ）。compile・`useDayModel` の `slotsOf` がこれを通す。`Problem` の形は変えない
- 振り直す訪問：欠勤の人の元の案の訪問のうち、始まった訪問（時間の約束のいちばん早い開始 ＜ いまの時刻。始まっている訪問・終わった訪問。2026-10-13 利用者が決定）を除き、その人に可にならない訪問（欠勤と重なる）と、残すと strict で回れなくなる訪問（間に合わない）
- 元の案：その日の確定した割当（`manualPlans[date]`）があればそれ、無ければ今の案（`aiPlans[date].routes`）
- 結果：今の案（`AiPlan.reassign` に元の案・使った欠勤・いまの時刻）にし、担当のいる訪問をすべて固定。記録にも `AiRun.reassign` を付けて残し、比較の画面で「欠勤前」と比べられる。種類を `kind` で持つ代わりに `reassign` の有無で表す（中身が要るため）。`method` は1回目 'insert' だけ
- 欠勤の取り消しでは今の案を戻さない。差の欄の「元の案に戻す」で戻す
- 細部（2026-10-13 利用者が推奨どおりに決定）：欠勤は1人1日1件、30分単位・午前／午後の境は 12:00、半端な時刻は30分に丸める、始まっている訪問も動かさない、候補から入れるとき訪問の時刻は変えない（間に合わなければ違反の赤い枠）、件数の上限は超えない、確定した割当を元にするとき今の案に未確定の変更があれば確認を出してから捨てる
- 1回目：PRD D26〜D33（欠勤の登録・案A・差・候補・固定と記録・取り消し・稼働時間の画面の印・Excel）。2回目：D34（案B）・D35（連絡の一覧）

## 理由とトレードオフ
- 得るもの：
  - 欠勤を消せば元の稼働時間に戻る。メモ（病院の付き添い）が残り、稼働時間の画面と予定の画面で「欠勤」と見せられ、2回目の連絡文にも使える
  - 案A は「他の人の担当・順番・開始時刻は変わらない」を規則として保証でき、テストで確かめられる。決定的で一瞬（Worker も要らない）。なぜその人に入ったか（増える移動・条件）を説明できる
  - 結果を今の案と固定にするので、手直し・「固定を残して組み直す」・「この割当で確定」・比較の画面をそのまま使える
  - reassign を分けたので、欠勤の運用の規則（始まった訪問・入れる順・いまの時刻）の変更が matching（条件 → 問題）・solver（焼きなまし）に波及しない
- 失うもの：
  - 案A は局所的なので、少し他の人を動かせば入る訪問も「入らない」に残る。候補（受けられる人・〇分ずらせば入る）を出して人が決める。2回目の案B で補う
  - 案A の位置は費用の増えが最小の局所的な選び方で、全体の最適ではない（AI案の点数は下がりうる）
  - 差し引く処理が compile と画面の2か所に入る（どちらも domain の同じ関数を呼ぶ）
  - 全訪問を固定するので、あとで AI に担当ごと組み直させたいときは固定を外すか「AI案を作る」が要る
  - 時刻が30分単位なので、10:15 の早退などは丸めて入れる

## 影響
- 要件：PRD D26〜D35、やらないこと（本人からの連絡の受付・通知の送信・複数日の一括入力・勤怠）
- 設計：契約 `absenceSchema`・`DemoData.absences`・`AiPlan.reassign`・`AiRun.reassign`（optional）・`src/contracts/reassign.ts`。domain の `withoutAbsences`、matching の `CompileInput.absences`、新しいコンポーネント reassign、store の repair、excel の「欠勤」シート、pages（欠勤の欄・差の欄・候補・比較の「欠勤前」・稼働時間の画面の印・`lib/absences`・`lib/runs`）
- 見直す条件：入らない訪問が多く、手で入れる手間が大きいと言われたとき（案B を早める）。1日に複数の欠勤の時間帯が要ると言われたとき（1人1日に複数件を許す）。始まっている訪問・時刻をずらす扱いが現場と合わないとき
