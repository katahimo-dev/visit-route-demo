# ADR-0009：予定とAI案を1画面に統合する

- 日付：2026-10-13
- 状態：採用

## 背景
「予定」（`#/schedule`）と「AI案」（`#/plan`）の2つの画面があり、どちらもその日の訪問を担当ごとの列に並べて、ドラッグで担当を移せた。
予定の画面は訪問の追加・編集・取消と、開始時刻の順だけの手作業の割当（下書き → 保存）、AI案の画面は AI案を作る・手直し（固定）・組み直す・「予定に採用」を持っていた。

- 同じ日の割当を2か所で触れ、どちらが正なのか分かりにくかった（AI案を「予定に採用」すると予定の画面の割当が書き換わる）
- 予定の画面には、AI案の画面にある地図の担当の絞り込み・区間の強調・理由（点の内訳）・浮かせた地図（MapDock）が無かった
- 比較の画面の地図は担当1人ずつの A・B の線だけで、予定（AI案）の画面と押したときの挙動が違った

利用者から「1つにまとめたい」との要望が出た（2026-10-13）。

## 選択肢
1. 案A：1画面に統合する（AI案の画面を土台に、上に訪問の一覧（畳める）を置く。`#/schedule` は `#/plan` へ移す）
2. 案B：1つの画面の中でタブ（訪問の一覧／割当）を切り替える
3. 案C：統合しない（文言・リンクだけ直す）

## 決定
案A（利用者が選んだ。2026-10-13）。

- 画面の名前は「予定」（`#/plan`）。上から：訪問の一覧（初期は畳む。時間・訪問先・所要・今の案での担当・注意・編集/取消。担当の選択は無い）、AIの操作、プリセットごとの案のカード、今の案（「この割当で確定」）、担当ごとの順番、地図、計算に入れなかった訪問
- 「予定に採用」は「この割当で確定」に改める。写す先は今までと同じ（`manualPlans[date]` と各訪問の `staffId`）。データの形・版は変えない
- 確定の状態：計算に入れた訪問について、今の案の担当と `manualPlans[date]` の担当（未割当を含む）がすべて同じなら「確定済み」、違えば「未確定の変更あり」、`manualPlans[date]` が無ければ「未確定」。計算に入れない訪問は、確定しても担当を変えないので比べない
- 訪問を押したときの「担当を選ぶ」をやめ、理由だけを出す（担当はドラッグで移す）
- 担当ごとの列の最後に「自宅まで N分」（最後の訪問先 → 自宅）を出す。帰りの分は `problem.travel[最後の訪問先の点][自宅の点]`（`matching/timing.ts` が帰りに使うのと同じ表）。押すと地図でその区間を強調する
- 担当ごとの順番と地図の部品（`lib/routeView.ts`・`components/routeView.tsx`）を予定と比較で共通にする。比較の地図も担当の色で A（点線）・B（実線）を描き、訪問・区間・担当を押したときの挙動と MapDock を予定とそろえる

## 理由とトレードオフ
- 得るもの：割当を触る場所が1つになる。訪問の編集と、地図・理由を見ながらの手直しを同じ画面でできる。比較と予定で地図の操作が同じになり、コードの重複も減る
- 失うもの：開始時刻の順だけの手作業の割当（AI を使わずに担当を選んで並べる）は無くなる。手で決めたいときは、AI案の訪問をドラッグして固定し、「固定を残して組み直す」で手直しする。画面が縦に長くなる（訪問の一覧は畳んで抑える）

## 影響
- PRD の D4・D13・D18〜D21・D24・D25、設計書の pages のルートとチェック項目を直した
- `domain/scheduleModel` の `assign`・`warningsOf` などは画面から使わなくなった（テストがあるので残す。`timesOf` はスタッフの画面、`reconcile` は `useDayModel` が使う）
- 見直す条件：AI を使わずに担当を決めたいという声が多ければ、「AI案を作らずに空の案から手で並べる」を足すことを考える
