# ADR-0039：重い画面と地図を別のチャンクに分け、計算の進み具合は外の入れ物で子だけ描き直す

- 状態：採用（2026-10-19）
- 関連：PRD D248・D249、ADR-0001（GitHub Pages・`base: './'`）・0006（Excel は押したときに読む）・0009（予定と AI案は1画面）

## 背景
ビルドの本体のチャンクが 1.33MB（gzip 420KB）あり、ホームを開くだけで日の予定・月の予定・空き状況・比較・相性と地図（Leaflet・leaflet.css）まで読んでいた。ホームに地図は出ない。Excel（ExcelJS）はすでに押したときだけ読む別のチャンク。

日の予定は AI案の計算中、Worker の進み具合（100msごと）を画面の state に入れていたため、4000行の画面全体を毎回描き直していた（作成1回で8〜11回）。

制約：GitHub Pages のサブパス・HashRouter・相対パス（`base: './'`）のまま。ルート・URL は変えない。e2e の速さの上限（画面を移る・帯が出る）を落とさない。

## 選択肢と決定

### 分け方
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| A：重い画面5つ（日・空き状況・比較・相性・月）を `React.lazy`、地図は `RouteMap` の中で本体を `lazy`。画面が出たら残りを先に読む | ホームで読む JS が3割減る。地図を使う画面（〈利用者さん〉の詳細・スマホ画面・まとめて置く）も呼び方を変えずに済む。先に読むので移るときに待たない | 直接開いた画面はチャンクを2段（本体 → 画面 → 地図）で読む。チャンクが増える | 採用 |
| B：すべての画面を `lazy` | 本体がさらに小さい | 週・〈利用者さん〉などよく使う画面も待ちが増える。変える所が多い | 不採用（今回は見送り） |
| C：`manualChunks` で vendor（React など）を分ける | キャッシュが効きやすい | 初回に読む量は減らない | 不採用 |

### 読み込み中の表示
`Suspense` は `AdminShell` の本文に1つ、画面ごとの ErrorBoundary（`key` が画面のパス）の外に置く。React Router 7 の移動は transition なので、表示済みの境界は前の画面のまま待ち、読み込みの表示を挟まない。直接開いたときだけ「画面を読み込んでいます…」（空のときの `.empty` の見た目・高さ 50vh）。地図は指定の高さの枠に「地図を読み込んでいます…」を出し、読み終わっても下が跳ねない。

先読みは `Suspense` の中の `PreloadWhenShown` が、開いた画面が出たあと `requestIdleCallback`（最長2秒）で始める（直接開いた画面のチャンクと取り合わない）。5つと地図を同時には読まず、日・月・空き状況・地図・比較・相性の順に1つずつ、1つ読み終わるたびにまた手が空くのを待つ（まとめて読んで実行すると、その間の操作・速さの計測を待たせる）。分けた画面を URL で直接開いたときは、起動の処理（データの読み込み・初期の案）と並べてその画面のチャンクをすぐ読み始め、地図を出す画面（日・比較・空き状況）は地図の本体も一緒に読み始める。

### 読めないとき
新しい版を公開すると古いチャンクは消えるので、古いタブで移ると読めない。通信が切れても読めない。`React.lazy` は失敗を覚えるので、そのままだと「データが壊れている」画面と［データを初期状態に戻す］が出て、［もう一度表示する］でも直らない。

- 画面の ErrorBoundary は、動的 import・CSS の読み込みの失敗（ブラウザ・Vite の文。`lib/chunkLoad` の `isChunkLoadError`）を見分け、「画面を読み込めませんでした」「新しい版が公開されたか、通信が切れています。再読み込みしてください」と［再読み込み］［もう一度表示する］を出す。初期状態に戻すボタンは出さない（データは壊れていない）
- 自動では読み直さない（保存は 300ms 間引いており、入力中の欄も失う）。［再読み込み］は待っている保存を書いてから 500ms 後に読み直す（`main.tsx` の初期状態に戻すと同じ待ち）
- ［もう一度表示する］は lazy を作り直して読み直す。ブラウザは読めなかったモジュールを同じ URL では読み直さないので、失敗の文にある URL（Chrome・Firefox）に `?retry=N` を付けて読む。URL が分からない（Safari）ときは元の import をもう一度呼ぶ（だめなら再読み込み）。失敗するたびに作り直すと React の描き直しのたびに読み直して止まらないので、作り直すのはこのボタンのときだけ
- 地図の本体だけ読めないときは、画面全体をエラーにせず、`RouteMap` の中の小さな境界が同じ高さの枠に「地図を読み込めませんでした」と［再読み込み］を出す（ほかの例外は外の ErrorBoundary へ）

`React.lazy` は読み終わったチャンクでも最初の描画で一度止まり、ホームから日の予定へ移るのが 200〜400ms 遅れた（e2e-progress の「案が全部ある月でも帯が出る」の head）。`lib/lazyComponent` で、読み終わったあとに描き始める部品は `lazy` を通さず直に描く（描き始めたときに決め、途中で替えない。替えると作り直されて状態が消える）。

### 進み具合
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| A：小さな外の入れ物（`lib/valueStore`）＋ `useSyncExternalStore`、読むのはバーと回数の部品だけ | 画面は計算の始まり・終わりだけ描き直す。案B の欄にも同じ入れ物を渡せる | 入れ物という仕組みが1つ増える | 採用 |
| B：進み具合の state を子に閉じ、Worker の知らせを子へ配る | React の state だけで済む | 計算を始める処理（画面側）から子の setState へ道を通す必要があり、子が2か所（操作の行・右の欄と案B） | 不採用 |
| C：`startTransition` で描き直しを遅らせる | 変える所が少ない | 描き直す量は減らない | 不採用 |

## 理由とトレードオフ
- 得るもの：ホームの初回に読む JS 1,332KB → 921KB（gzip 419KB → 296KB）。地図のコードと CSS はホーム・週・データなどで読まない。計算中の日の予定の描き直し 8〜11回 → 1回（進み具合の部品だけが毎回描き直す）
- 失うもの：先読みが終わる前にまだ読んでいない画面へ移ると、読み終わるまで前の画面のまま待ち、待っている印は出さない（今回は入れない）。直接開いた日の予定は、本体・画面・地図のチャンクを順に読む（通信の往復が増える）。先読みのぶん、全部の画面を開かなくても最終的に読む量は前とほぼ同じ。CSS は画面のチャンクと一緒に後から入る（計算した見た目が前と同じなことを、直接開く・別の画面から移るの両方で確かめた）

## 影響
- 設計書：design.md §4 pages（読み込みの分け方・よく変わる値）・deploy の完了の条件・§7
- 見直す条件：週・〈利用者さん〉など本体に残る画面が重くなったとき（案B）。案を比べるの「もう1案」の進み具合も画面の state のまま（同じ入れ物に移せる）
