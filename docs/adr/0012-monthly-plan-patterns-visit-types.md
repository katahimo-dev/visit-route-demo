# ADR-0012：訪問の種類・定期パターンから一月分の訪問と案を作り、月・週・空き状況で見渡す

- 日付：2026-10-16
- 状態：提案（方向は 2026-10-16 に利用者が決定。細部は下の「決定」の推奨で、利用者の確認待ち＝PRD §8・design.md §8）

## 背景
利用者から次の要望が出た（2026-10-16）。

1. 一月分の案を、まず標準の条件でまとめて作りたい。他の条件の案は、その日を開いてボタンを押したときに作ればよい
2. 週・月の予定を一覧で見たい。週では**スタッフの偏り**と**時間軸**を見たい
3. 月の一覧で「どの曜日のどの時間が空いているか」を見たい。いまは新規の問い合わせに空き状況を即答できず、**機会を逃している**
4. 一月分の訪問は、利用者さんごとの**定期パターン**から作り、ドラッグで日時をずらしたい
5. 訪問に**種類**（介護・リハビリ）が欲しい。種類によって担当に必要な条件が変わる。別法人で家事代行・ベビーシッターもあるので、種類は**利用者が自由に足せる**ようにしたい

いまは、AI案は1日単位で、訪問は日ごとに1件ずつ入れる（seed は今日から14日分を作る）。PRD §4 は「月次シフトの一括作成」をやらないことにしている。
担当に必要な条件は、利用者さんの必要条件（`clients[].requirements`。条件の型 `clientRequirement`）だけで持っている。

決めること：(1) 一月分の訪問の出どころ、(2) 展開した訪問の持ち方、(3) 種類の条件の効かせ方、(4) 一月分の案の作り方、(5) seed の扱い、(6) 作る順番、(7) 別法人の扱い。

## 選択肢
1. 一月分の訪問の出どころ
   - A：**定期パターン**（利用者さんごと。種類・曜日・間隔・時刻・所要・期間）から展開する
   - B：Excel で一月分の訪問を一括で読み込む（いまの D23 のまま）
   - C：前の週をコピーする（いまの「前の同じ曜日からコピー」の週版）
2. 展開した訪問の持ち方
   - A：**訪問として実体化**し、元のパターン・元の日・「この回だけ変えた」の印を持たせる
   - B：訪問は持たず、パターンと「例外（この回だけの変更・取り消し）」から毎回計算する
3. 種類の条件の効かせ方
   - A：**種類のマスタ**に担当に必要な条件を持たせ、常に必須（可否で外す）として効かせる。条件の型は増やさない
   - B：条件の型 `typeRequirement` を足し、重み・必須を利用者が選べるようにする（プリセットの表・Excel の列も増える）
   - C：種類を選ぶと、その条件を利用者さんの必要条件に写す
4. 一月分の案の作り方
   - A：**1日ずつ**、基準のプリセット（点数の基準のプリセット。初期は標準）の重みで、いまの Worker で順に解く
   - B：1日ずつ、全プリセットで解く（いまの D21 を月に広げる）
   - C：月全体を1つの問題にして解く（日をまたいだ均等・継続を最適化する）
5. seed
   - A：**定期パターンを持たせ**、いまの14日分の訪問はパターンの展開で作る（いまの訪問と同じ日・時刻・所要・ID になるようにする）
   - B：いまのまま（日ごとの訪問）。定期パターンは空で始める
6. 作る順番：段階1（種類・定期パターン・月まとめ作成・月間カレンダー）、段階2（週間の時間軸・ドラッグ・スタッフ×曜日の表・D21 の見直し）、段階3（空き状況の表・問い合わせの試算）の順
   - A：1→2→3
   - B：**1→3→2**（機会損失を先に減らす）
7. 別法人
   - A：**データを分ける**（別のブラウザ・別の JSON／Excel。いまの「1ブラウザ1事業所」のまま）
   - B：1つのデータに法人を持たせて分ける

## 決定
1-A、2-A、3-A、4-A、5-A、6-B、7-A。1-A（パターンから展開・ドラッグでずらす）・6-B・種類を自由に足す は利用者が決定（2026-10-16）。残りは推奨で、利用者の確認待ち。

- 種類（`DemoData.visitTypes`）：名前・色・標準の所要時間・担当に必要な条件（`Condition[]`。スタッフの特性に対して）。最大20。訪問・定期パターンは `typeId`（null＝種類を問わない）。matching の `compile` は、種類の必要条件を満たさない組を**必須で外す**（理由の `ruleId: 'visitType'`）。条件の型・プリセットの表・点数の物差しは変えない
- 定期パターン（`DemoData.patterns`）：利用者さん・種類・曜日（複数）・間隔（1〜4週ごと。`from` を含む週を1週目）・時間の決め方と開始・所要・`from`〜`to`（null＝続く）・いつもの担当（null＝利用者さんのいつもの担当）・メモ
- 展開：新しいコンポーネント patterns（`src/patterns/`。純粋関数）。訪問の ID は `${元の日}_${パターンID}`（決定的。同じパターン・同じ日は同じ訪問）。訪問に `typeId` と `pattern: { id, date（元の日）, edited（この回だけ変えた） } | null` を足す。すでにある ID は作らない（この回だけの変更・取り消しが残る）。今日より前の日は作らない
- パターンを直す（「以降すべて」）：「いつから」の日でパターンを分け（元のパターンの `to` を前日にし、新しいパターンを足す）、その日以降の `edited` でない訪問（元のパターンのもの）を消して新しいパターンから展開し直す
- 月まとめ作成：画面（`lib/month`）が、その月の今日以降の訪問のある日を順に、基準のプリセットの重みで compile して Worker で解き、今の案と記録に1日ずつ書く。対象は「まだ案の無い日だけ」（初期値）か「確定していない日をすべて作り直す」。確定した日は触らない。止めると今の日はそれまでの最良で残し、残りはやめる。他のプリセットの案は作らない（D20 のカードで作る）
- seed：利用者さん1人に定期パターン1つ（いまの「平日のうち1つの曜日だけ休み・印があれば土日も」の規則をそのまま曜日にする）。パターンの ID は利用者さんの ID と同じにして、展開した訪問の ID がいまと同じ（`${日付}_${利用者さんID}`）になるようにする。種類は「介護」「リハビリ」（初期データ）。いまの訪問はすべて担当できる人が変わらないように種類を付ける（子どもの対象の利用者さんは種類なし）。リハビリの動きを見せるため、資格に理学療法士などを足し、高齢の利用者さん2人に週1回のリハビリのパターンを足す
- 空き状況・問い合わせの試算（段階3）は、欠勤の振り直しの案A（他の人の担当・順番・開始を変えずに空き時間へ入れる。ADR-0011）と同じ考え方で、先4週の今の案に入れてみて判定する。細部は段階3の着手前に、この ADR に追記する

## 理由とトレードオフ
- 得るもの：
  - 定期パターンは実際の業務（決まった曜日・時刻の繰り返し）に合い、一月分を1回の操作で作れる。問い合わせの試算（段階3）でも「週1回・火曜」を同じ形で扱える
  - 訪問を実体化するので、いまの予定の画面・AI案・手直し・確定・欠勤・比較・Excel が、訪問の形をほぼ変えずにそのまま動く。この回だけの変更は訪問を直すだけで残る
  - 種類の条件を常に必須にすると、条件の型・プリセット・点数の物差し（ADR-0010）に波及しない。「リハビリは資格のある人だけ」は業務上も外せない条件
  - 種類は利用者が足せるので、介護・リハビリ・家事代行・ベビーシッターのどの法人でも同じ画面で使える
  - 1日ずつ基準のプリセットで解けば、いまの solver・記録・カードをそのまま使え、一月（約30日）でも数分で終わる。止めても作れた日は残る
  - seed をパターンにしても訪問がいまと同じなので、いまのテスト・ベンチマークの前提（seed の14日）が崩れにくい
- 失うもの：
  - 実体化した訪問はパターンと二重に持つ。パターンを直したとき「以降すべて」で作り直す処理と、`edited` の印の管理が要る。展開した月が増えるほど localStorage の容量を使う（一月で訪問 約500件・案と記録 約30日分。数百KB の見込み。超えたら書き出しを促す。古い月の片づけは今回やらない）
  - 種類の条件を重みで緩めることはできない（緩めたい声が出たら 3-B に移す）
  - 月まとめ作成は日ごとの最適で、月の件数の均等・同じ人が続けて担当する並べ方は最適化しない（段階2の表で偏りを見て、手直しする）
  - 他のプリセットの案は作らないので、カードの比較は日を開いてから
  - seed にリハビリの訪問を足すと、その日の案の結果（点数・ベンチマークの数値）は変わる（`docs/optimization-benchmark.md` の数値は前の seed のもの）
  - 別法人を1つのデータで切り替えることはできない（データを分けて使う）

## 影響
- PRD：D36〜D52 を追加。§4 の「月次シフトの一括作成」を「勤務シフトの自動作成・日をまたいだ最適化はしない」に書き直し、事業所の分離・パターンの月単位の指定・試算での入れ替えをやらないことに足す
- design.md：コンポーネント patterns を足す。store（`visitTypes`・`patterns`・訪問の `typeId`・`pattern`）・seed（種類・パターン）・matching（種類の必須）・excel（「種類」「定期パターン」シート・訪問の列）・pages（`#/month`・種類と定期パターンの画面・月まとめ作成）を変える。契約は §5「訪問の種類と定期パターン」
- データ：`DATA_VERSION` は1のまま（`visitTypes`・`patterns` は zod の既定値 `[]`、訪問の `typeId`・`pattern` は既定値 null。`absences` を足したときと同じ）
- 見直す条件：種類の条件を重みで緩めたい声が出たら 3-B。月の均等・継続を最適化したい声が出たら 4-C を検討。容量が足りなくなったら IndexedDB へ移す（design.md §7 の保存の行）
