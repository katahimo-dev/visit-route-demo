# ADR-0012：訪問の種類・定期パターンから一月分の訪問と案を作り、月・週・空き状況で見渡す

- 状態：採用（2026-10-16）
- 関連：PRD D36〜D57、ADR-0010（点数の基準）、ADR-0011（案Aの考え方）

## 背景
利用者から次の要望が出た。
1. 一月分の案をまず標準の条件でまとめて作りたい（他の条件の案は、その日を開いて押したときに作る）
2. 週・月の予定を一覧で見たい（週ではスタッフの偏りと時間軸）
3. 「どの曜日のどの時間が空いているか」を見たい。新規の問い合わせに空き状況を即答できず機会を逃している
4. 一月分の訪問は利用者さんごとの定期パターンから作り、ドラッグで日時をずらしたい
5. 訪問に種類（介護・リハビリ）が欲しい。種類で担当に必要な条件が変わる。別法人（家事代行・ベビーシッター）もあるので、種類は利用者が自由に足せるようにしたい

当時、AI案は1日単位で訪問は日ごとに1件ずつ入れ、PRD §4 は「月次シフトの一括作成」をやらないとしていた。担当に必要な条件は利用者さんの必要条件（`clients[].requirements`）だけで持っていた。
決めること：一月分の訪問の出どころ・展開した訪問の持ち方・種類の条件の効かせ方・一月分の案の作り方・seed・作る順番・別法人の扱い。

## 決定
定期パターンから展開して訪問を実体化し、種類のマスタの条件を必須で効かせ、1日ずつ基準のプリセットで解く。seed もパターンの展開で作る。作る順番は 月の一括作成 → 空き状況 → 週間の時間軸。別法人はデータを分ける。

- 種類（`DemoData.visitTypes`）：名前・色・標準の所要時間・担当に必要な条件（スタッフの特性に対する `Condition[]`）。最大20。訪問・定期パターンは `typeId`（null＝問わない）。matching の `compile` は種類の必要条件を満たさない組を必須で外す（理由の `ruleId: 'visitType'`）。条件の型・プリセットの表・点数の物差しは変えない
- 定期パターン（`DemoData.patterns`）：利用者さん・種類・曜日（複数）・間隔（1〜4週ごと。`from` を含む週が1週目）・時間の決め方と開始・所要・`from`〜`to`（null＝続く）・いつもの担当・メモ
- 展開：新コンポーネント patterns（`src/patterns/`。純粋関数）。訪問の ID は `${元の日}_${パターンID}`（決定的）。訪問に `typeId` と `pattern: { id, date, edited } | null` を持つ。既にある ID は作らない（この回だけの変更・取り消しが残る）。今日より前は作らない
- パターンを直す（「以降すべて」）：「いつから」の日で分け（元の `to` を前日にして新パターンを足す）、その日以降の `edited` でない訪問を消して展開し直す
- 月まとめ作成：その月の今日以降の訪問のある日を順に、基準のプリセットの重みで Worker で解き、今の案と記録に1日ずつ書く。対象は「まだ案の無い日だけ」（初期値）か「確定していない日をすべて」。確定した日は触らない。止めても今の日は最良を残す。他のプリセットの案は作らない
- seed：利用者さん1人に定期パターン1つ（既存の曜日の規則をそのまま曜日にし、パターン ID を利用者さんの ID と同じにして、展開した訪問の ID・日時・所要がこれまでと一致するようにする）。種類は「介護」「リハビリ」。リハビリの動きを見せるため資格に理学療法士などを足し、高齢の利用者さん2人に週1回のリハビリのパターンを足す
- 空き状況・問い合わせの試算は、先4週の今の案に入れてみて判定する（案Aと同じ考え方。細部は ADR-0013 ほか）
- 月間・週間の改定（2026-10-17。PRD D53〜D57）：月間に点数は出さず、状態は色と印で表す。午前・午後の空きの割合（D48）は分かりにくかったので、時刻つきの混み具合バー（30分ごとの空き人数を赤・橙・緑）に置き換え、種類で数える人を絞れる。月間でスタッフ・利用者さんを1人選んで詳細を出す。週間は複数選択・資格バッジ・ドラッグ中の「入れる人 N人」・利用者さん×曜日の表
- 画面・Excel の列などの細部は design.md

## 検討した案
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| 出どころA：定期パターンから展開 | 実業務の繰り返しに合う。一括で作れる。問い合わせの試算も同じ形 | パターンと訪問の二重管理 | 採用 |
| 出どころB：Excel で一月分を一括読込 | 既存 D23 のまま | 入力の手間が大きい | 不採用 |
| 出どころC：前の週をコピー | 簡単 | 曜日・間隔・期間を表せない | 不採用 |
| 持ち方A：訪問として実体化 | 予定・AI案・手直し・確定・欠勤・比較・Excel がそのまま動く。この回だけの変更は訪問を直すだけ | `edited` 管理と作り直しの処理が要る | 採用 |
| 持ち方B：パターン＋例外から毎回計算 | 二重にならない | 既存機能すべてに波及 | 不採用 |
| 種類3-A：種類のマスタの条件を常に必須 | 条件の型・プリセット・物差しに波及しない。業務上も外せない条件 | 重みで緩められない | 採用 |
| 3-B：条件の型 `typeRequirement` を足す | 重み・必須を選べる | プリセットの表・Excel の列が増える | 緩めたい声が出たら |
| 3-C：種類を選ぶと利用者の必要条件へ写す | 型を増やさない | 種類を変えても条件が残る | 不採用 |
| 案の作り方4-A：1日ずつ基準のプリセット | 既存の solver・記録・カードで、一月でも数分 | 月の均等・継続は最適化しない | 採用 |
| 4-B：1日ずつ全プリセット | 比較できる | 時間が3倍ほど | 不採用 |
| 4-C：月全体を1問題 | 日をまたいだ均等・継続 | 重く、既存と合わない | 声が出たら検討 |
| seed A：パターンを持たせ同じ訪問を展開 | 既存のテスト・ベンチマークの前提が崩れにくい | リハビリを足すと点数・数値が変わる | 採用 |
| seed B：日ごとの訪問のまま | 変更なし | パターンの動きを見せられない | 不採用 |
| 順番 1→2→3／1→3→2 | 後者は機会損失を先に減らせる | — | 1→3→2 を採用 |
| 別法人A：データを分ける（1ブラウザ1事業所のまま） | 簡単 | 切り替えられない | 採用 |
| 別法人B：1データに法人を持たせる | 切り替えられる | 全体に波及 | 不採用 |

## 結果・トレードオフ・見直す条件
- 得るもの：一月分を1回の操作で作れる。既存の画面・機能が訪問の形をほぼ変えずに動く。種類を足せるのでどの法人でも同じ画面で使える。一月（約30日）でも数分で終わり、止めても作れた日は残る
- 失うもの：
  - 展開した月が増えるほど localStorage を使う（一月で訪問約500件・案と記録約30日分で数百KB。超えたら書き出しを促す。古い月の片づけは今回やらない）
  - 種類の条件を重みで緩められない。月まとめは日ごとの最適で、月の均等・継続は最適化しない（週の表で偏りを見て手直し）
  - 他のプリセットの案は日を開いてから。seed にリハビリを足したので結果・ベンチマーク（`docs/optimization-benchmark.md`）は旧 seed のもの
  - 別法人を1データで切り替えられない
- 見直す条件：種類の条件を緩めたい声（3-B）。月の均等・継続の最適化（4-C）。容量不足（IndexedDB へ。design.md §7）
- 影響：PRD §4 の「月次シフトの一括作成」を「勤務シフトの自動作成・日をまたいだ最適化はしない」に書き換えた。`DATA_VERSION` は1のまま（`visitTypes`・`patterns` は既定値 `[]`、訪問の `typeId`・`pattern` は null）
