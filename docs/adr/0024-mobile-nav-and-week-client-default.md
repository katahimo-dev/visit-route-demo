# ADR-0024：スマホのメニュー（上の帯・引き出し・下のタブ）と、週間の時間軸の〈利用者さん〉の初期値

- 状態：採用（2026-10-18）
- 関連：PRD D132〜D140、ADR-0019（メニュー）、ADR-0021（表の絞り込み）、ADR-0027（メニューの並びの後の変更）

## 1. スマホのメニュー

### 背景
狭い画面（幅860px以下）では左のメニューが上に横一列で並ぶ。
- 13項目が横に並び、巻かないと見えない
- グループの見出しを隠しているので、〈利用者さん〉と〈スタッフ〉の「一覧・編集」が見分けられない
- 右下の地図・左下の欠勤の振り直しの帯・トーストは、画面の下端からの位置を CSS の変数で避け合っている
- 端末の前提は「管理者役は PC、スマホは表示の確認」（PRD §7）なので、各画面の中身はスマホ向けに作り直さない

### 決定
上の帯にロゴと今の画面の名前（グループの見出し＋項目名）・「メニュー」・日付の切り替えを置く。「メニュー」で左から引き出し（全メニューを見出し付きの縦並び。dialog）を開く。下によく使う4つ（月・週・日・空き状況）のタブを常に並べる。

- 決まりは `lib/nav.ts`（純粋関数）の1か所：今の画面をどの項目と見るか（`activeNavPath`。比較は日の続きなので「日」）、上の帯の名前（`navTitle`）、下のタブ（`bottomTabs`）。引き出しは `app/NavDrawer.tsx`（`SidePanel` と同じ閉じ込め・フォーカスの戻し方）。下のタブの高さは `--bottom-tabs-h`（広い画面・印刷では0）にし、浮いている部品・本文の下の余白・トーストはこの変数で避ける
- 今の画面の項目（引き出し）・下のタブを押し直しても移り直さない（URL のクエリ＝画面の状態を消さない）
- 引き出しは body 直下に出し、開いている間 `#root` を inert にする。`aria-haspopup="dialog"`・開いているときだけ `aria-controls`・一覧は「画面の一覧」・見出し h2。裏のロックは数を数える `useBodyScrollLock`（`lib/scrollLock`）にまとめ、右の欄と重なっても最後の1つまで戻さない。開いたまま広い画面へ戻したらフォーカスは左のメニューの今の項目へ
- viewport に `viewport-fit=cover` を足し、上の帯・本文・タブ・引き出し・地図・〈スタッフ〉のスマホ画面の余白を safe-area で避ける（Chromium では 0 なので実機の横向きは未確認）
- 印刷：下のタブ・引き出しは出さない。用紙の幅が860px以下（A4縦）では上の帯も出さず、本文は1列。A4横は広い画面の決まり
- データ・契約・URL は変えない。確かめ方は `scripts/e2e-mobile.cjs`（390×844 と 1400px）
- メニューの並び・名前は ADR-0027 で用途ごとに変わった（上の帯の名前は「グループの見出し・項目名」のまま、比較は上の帯・引き出しでは「案を比べる」、下のタブでは「日」。上の帯の1段目に「探す」が増えた）

### 検討した案
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| A：上の帯＋引き出し＋下のタブ4つ | 巻かずに全メニューへ（2手）。よく使う画面は1手。名前で一覧・編集を見分けられる。広い画面は変わらない | 上の帯が2段になることがある。下のタブぶん本文が狭くなる（約58px＋ホームバー）。項目が2か所に描かれる（同じ部品 `NavGroups`） | 採用 |
| B：横一列のまま見出しだけ出す | 変更が小さい | 横に巻くのが残る | 不採用 |
| C：下のタブだけ（残りは「その他」） | シンプル | 「その他」がもう1枚の画面になり、見出しの問題が残る | 不採用 |
| D：引き出しだけ | シンプル | よく使う画面にも毎回2手 | 不採用 |

### 結果・見直す条件
- 狭い画面で上の帯が2段のとき、帯の高さを測って `--header-h` に出し、貼り付く要素がずれないようにする
- 見直す条件：スマホで予定を直す使い方が増えたら、各画面の中身（表・時間軸）のスマホ向けの作りを別に決める。下のタブの4つはデモの反応で入れ替える
- 狭い画面の一覧の表・格子の表・週の既定は [ADR-0033](0033-narrow-tables-as-cards.md) で決め直した（「各画面の中身はスマホ向けに作り直さない」を置き換える）

## 2. 週間の時間軸「〈利用者さん〉で見る」の初期値

### 背景
週間の時間軸の「〈利用者さん〉で見る」は、検索欄で人を選ぶ（8人まで・`?client=`。PRD D61・D62・D108）。
- 選んでいないと空で、開くたびに近道か検索で選び直す手間がかかる（利用者の要望）
- 〈スタッフ〉で見るときはチップで全員が並び、選ばなくても全員が出る。見る人によって操作が違う
- 表（〈利用者さん〉×曜日。ADR-0021）から移ったときだけ、選択が空なら表の先頭8人を引き継ぐ。初期値を足すと「空なら」の条件と食い違う
- 表の絞り込みは `?cf=` で、既定のままなら URL に書かない

### 決定
この週に訪問がある人をチップで並べ（表の既定と同じ人・同じ順）、`?client=` が無ければ先頭8人を初期値にする（URL に書かない）。検索欄は「ほかの人を探す」に畳んで残す。表からの引き継ぎは「`?client=` があればそれ。無ければ、表で絞り込んでいればその先頭8人、絞り込んでいなければこの週の先頭8人」。

- 決まりは `lib/timelineClients.ts`（純粋関数）の1か所：`defaultTimelineClients`・`timelineSelection`・`clientParamOf`（初期値と同じ人なら書かない）・`timelineChipIds`・`handoffFromTable`。チップは〈スタッフ〉と同じ `PickChips`（`actions` で「全部外す」「先頭8人に戻す」）、検索欄は `ClientPicker`（`showChips={false}`）
- 畳む（PRD D140）：選んでいる人と上から2行ぶんだけ出し、残りは「あと N人」で開く。選んでいる人は2行に入らなくても出し、並び順は変えない（押した人が動かない）。開いているかは画面の中だけで覚える。行は描いた位置（上端）で数える（`lib/fold` の `foldHidden`。幅・人・選んでいるかが変わったときだけ測り直す）。390px では選んでいる8人だけで4〜5行になり、時間軸の上端は最初の画面の少し下（約930px／844px）、1400px では最初の画面に入る（約530px）
- `?client=` の意味は「あればそれ」で従来と同じ（無いときが「空」から「先頭8人」に変わる）。データ・契約は変えない。確かめ方は `e2e-drag.cjs`・`e2e-details.cjs`・`e2e-week.cjs`

### 検討した案
| 案 | 長所 | 短所 | 採否 |
|---|---|---|---|
| A：チップ＋先頭8人を初期値（URL に書かない） | 開いたらすぐ帯が見え、〈スタッフ〉と同じ操作。週を送るとその週の人になる。URL が短い。引き継ぎと初期値が1つの決まりになる | 訪問のある人が多いとチップが何行にもなる（今のデータ20人で1400pxは4行、390pxは10行ほど）→畳むで対処 | 採用 |
| B：初期値を URL に書く | 明示的 | 週を送ると前の週の人が残り、URL が長い | 不採用 |
| C：検索欄のまま初期値だけ先頭8人 | 変更が小さい | 〈スタッフ〉と操作がそろわず、だれが選ばれているか一目で分からない | 不採用 |
| D：引き継ぎは今のまま | 変更なし | 空なら引き継ぐ条件が初期値と食い違う | 不採用 |
| 畳む1（採用）：選んでいる人と2行ぶん＋「あと N人」 | 押した人が動かない | — | 採用 |
| 畳む2：選んでいる人を前へ並べ替え | 見えやすい | 押すたびに位置が変わる | 不採用 |
| 畳む3：チップにも絞り込みの欄 | 絞れる | 20人では重い | 不採用 |

### 結果・見直す条件
- 「全部外す」のあと（`?client=` が空）は週を送っても空のまま（明示して外したので）。表で絞り込んで移ったあとは `?client=` に書くので、週を送っても同じ人のまま
- 見直す条件：訪問のある人が数十人の事業所でチップが長すぎれば、チップも `ClientFilter` で減らすか「もっと見る」で畳む。390px で時間軸まで遠いという声があれば、狭い画面では選んでいる人も「あと N人」に含めるかを決める
